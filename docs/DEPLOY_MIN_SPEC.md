# 新设备最小化部署接入（DEPLOY MIN SPEC）— v6.5.0

> **这一页只回答一个问题：一台新设备要装多少东西，才能成为本网络的可用节点？**
> 答案：**一个 1.7 MB 的包（不带运行时）/ 约 0.4 GB 的包（带运行时）**，
> 会话、归档、索引、备份**一个都不装**——那些等连上节点再按需拉。

---

## 一、要解决的三件事

1. **悖论**：想部署必须先复制，复制了才能连节点。→ 把"复制"缩成一次性的**最小引导**，其余交给连接。
2. **体积**：整库 5 GB、其中索引 2.8 GB 可重建；整包复制等于把老路再走一遍。→ 只带**点火器**。
3. **安全**：包会在机器之间流动。→ 包里**不许有密钥**，带 MANIFEST 逐文件校 sha256。

## 二、三层，各管一段，互不依赖

| 层 | 干什么 | 靠什么 | 失败时 |
|---|---|---|---|
| ① 引导 bootstrap | 让新设备**能跑起来** | 纯文件复制（离线可完成）+ `persona_bootstrap.py` | 校验不过就拒装，不进入下一层 |
| ② 认身份 identity | 让它**知道自己是哪台** | 机器配置（默认 → 探测 → 机器档 → 生效） | 认不出就生成新机器档，**绝不猜成旧机器** |
| ③ 连接 join | 让它**和别人同步** | 节点服务（局域网/虚拟组网）+ 统一令牌 | 连不上 → 退化成**单机可用**，功能降级而不罢工 |

**关键**：三层失败互不传染。连不上照样是可用节点；重客户端可以被策略关掉（配置里 `clients.<名字>.enabled=false`），关掉照样能跑。

## 三、最小引导包：装什么，不装什么

| 内容 | 体积（实测） | 带？ | 理由 |
|---|---|---|---|
| `scripts\`（脚本本体） | ~1.6 MB | ✅ | 全部能力都在这里 |
| `config\`（默认 + 机器档） | < 100 KB | ✅ | 配置跟着库走，重装不丢 |
| `docs\`（先读我 / 使用说明 / 接入手册 / 自检清单 / 本页） | ~40 KB | ✅ | 到现场能自己看 |
| `runtime\`（独立 python / node / git） | ~0.4 GB | ⚠ 选带 | 目标机没有 python 就必须带 |
| `sessions\` / `archive\` / `index\` / `备份\` / `ops\` / `续接\` | 数 GB | ❌ | 数据与运行态，由连接按需拉 |

实测（本机，2026-11-12）：**不带运行时 111 个文件 / 1.7 MB**；`verify` 全绿（OK 111 · 哈希不符 0 · 缺 0）。
**带运行时**：5684 个文件 / 396.8 MB → 压成 **156 MB** 的 zip，`verify` 同样全绿（OK 5684 · 不符 0 · 缺 0），
打包耗时 132 秒（4 GB 内存小主机）。

### 3.1 命令

```bash
python persona_bootstrap.py list                       # 只列：会打什么、多大、跳过了什么
python persona_bootstrap.py pack --out <目录> --version 6.5.0
python persona_bootstrap.py pack --out <目录> --with-runtime   # 连运行时一起
python persona_bootstrap.py verify <zip>               # 按 MANIFEST 校 sha256
python persona_bootstrap.py init --root <解压目录> --apply     # 建目录骨架（开场那一步）
```

**为什么要 `init`**（2026-11-12 拿真包解压实测发现）：包里只有 `scripts/ config/ docs/`，
解出来直接跑会发现 `ops/ sessions/ archive/ index/ 备份/ 续接/ steps/ memory/ 清理/` 都不存在。
脚本大多能自己建，但**建的时刻不确定**，报错看起来像故障。所以给一条明确的"开场"：
先把骨架摆好，再谈认身份与连接。

### 3.2 三条硬规则（写在代码里，不靠记性）

1. **禁收目录**：`sessions` / `archive` / `index` / `备份` / `ops` / `清理` / `续接` / `steps` 一律不进包——
   扫到就**拒绝打包**（退出码 3），不是"跳过"。
2. **禁收密钥**：文件名像令牌/凭据（`token` / `credential` / `secret` / `.env` / `.key` / `id_rsa`）就拒；
   内容里扫到 `sk-` 开头的长串或私钥头也拒。
3. **必须能自证**：包里一定有 `MANIFEST.json`（每文件 sha256 + 总大小 + 生成时间），
   `verify` 不通过就**不许装**。

## 四、接上网络的顺序

```
① 解包 → verify → selftest 全绿        → 此时是【单机可用】
② 认身份（生成/复用本机配置）           → 仍是单机
③ 填统一令牌 → /health 探活             → 分清"网络不通"还是"令牌不对"
④ 先 --dry-run 看清单，再只拉需要的目录  → 变成【节点可用】
⑤ 自检 → 记账
```

**约定**（端口与凭据属部署契约，不属实现细节）：

| 项 | 约定 |
|---|---|
| 端口 | 固定 **8737/TCP**；客户端主动外连，不需要反向端口 |
| 监听 | 只监听**虚拟组网网卡**地址；默认安全档是只监听回环，不外露 |
| 防火墙 | 只放行虚拟网段到该端口；物理局域网不放行 |
| 凭据 | **一份共享令牌，全节点同一份**；不进库、不进包、不进 git、不进快照 |
| 同步方向 | 新节点**只拉不推**；要它干活走任务池派发，不直接改对方文件 |

## 五、边界（这一版明确没做）

- **没有**"一键把整库搬到新设备"——那正是本规格要拆掉的老路；
- **没有**双向自动合并：两边同时改同一份记忆的冲突留给人和下一版，冲突就停下；
- **没有**打包器的图形界面，也没有"从远端拉引导包"——引导包必须能**离线**用；
- 端口的**多地址监听 / 防火墙放行 / `health` 探活**已在 **v6.8.0** 落地：
  `serve --bind 127.0.0.1,<虚拟IP>`（逗号分隔，各起一个）、`firewall --allow <CIDR>`（默认只打印命令，`--apply` 才执行）、
  `health --server <url>`（**不需要令牌**，用来分清网络不通还是令牌不对）。
