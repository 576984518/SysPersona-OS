# SysPersona Runtime 规范（现行）

**Persona Runtime Specification — 加载、组装、路由、执行、归档**

> 状态：**规范（Normative）**，与 v1.0.0 方法规范同级。
> 现行版本：**v1.1**（持续修订，不单独发版）｜ 位置：`docs/LAUNCHER_SPEC.md`
> 配套：`docs/MIDDLEWARE_LAUNCHER.md`（实测与取舍）、`docs/SECURITY_SPEC.md`（容器与密钥）
> 关键词：**MUST / MUST NOT / SHOULD / MAY** 按 RFC 2119 解释。

## 0. 摘要

> 术语：「人格」指设定文件（规则与记忆的文件形态）；重载=重置；统一叫记忆分身。见 README「它解决什么」一节末。

Runtime 管的是「它」的**生命与能力**：从哪个文件醒来、这一轮看见什么、允许它做什么、由谁回答、做完之后沉到哪里。

它不转发流量。转发只是它最窄的一种用途。

**唯一的判据**：一个实现只要独立承担下面五件事，并把规则与记忆存成可随人走的文件，它就是合规的 Runtime。

1. **加载**：从任意数据源取出三层设定文件与记忆，校验完整性；
2. **组装**：在预算内检索记忆，把「它是谁 + 它记得什么 + 你刚说了什么」拼成一次请求；
3. **路由**：把请求交给可替换的模型，并让降级可见；
4. **执行**：模型想动文件、联网、跑命令、开摄像头——由 Runtime 判定能不能做、替它做、并记下做过了什么；
5. **归档**：把这一轮（包括动作）沉淀下来，在睡眠时固化，在崩溃后能恢复。

端口、进程、语言、有没有 HTTP，都不参与判定。

| 形态 | 结构 | 达到同一目的的代价 |
|---|---|---|
| **`embedded`** | 库嵌进 App，直接读写本地文件 | 只能自用，第三方 UI 接不进来 |
| **`gateway`** | 独立进程 + OpenAI 兼容 HTTP | 需要一台常开的机器 |
| **`host-client`** | 家里主机为 origin，设备为薄客户端 | 最复杂，离线要收敛 |

**目标不是「在某一台设备上不失忆」，而是「换设备不失忆」。**

前者用 `direct` 就能做到——文件在本地，这台机器永远记得你；但换一台手机，你得拷文件、拷密钥，那叫搬运，不叫连续。
后者只有 `managed` 能做到：客户端手里只有一个口令，文件永远在服务端。**换设备 = 在新设备输入口令，而不是复制一份文件。**

所以：`managed` 是目标形态，`direct` 是单设备回退。两者都合规，但只有一个实现得了这个项目要的东西。

**在场不强制唯一**：可以一次只醒一个地方（`exclusive`），也可以多条时间线并行、事后收束（`concurrent`）。两种都合规，差别是代价，见 §5.5。

### 0.1 三个东西各是什么

| | 是什么 | 换掉会怎样 | 粗略的类比 |
|---|---|---|---|
| **设定文件**（规则与记忆的文件形态） | 身份、边界、记忆 | 换掉就是另一份规则与记忆（记忆分身换了） | 规则书 / 基因 + 日记 |
| **模型** | 推理与语言能力 | 换掉只是换了智力与口音 | 借来的大脑 |
| **Runtime** | 加载、裁决、执行、归档 | 关掉就"假死"，但文件还在 | 身体 |

精确一点，这个类比有三处要修正：

1. **身体不止一具。** PC、手机、机器人都可以是；但同一时刻只有一个"醒着"（§5.5）——不是因为它只能有一具身体，是因为同时醒两个就成了两个它。
2. **连续性不靠身体。** 每次唤醒都是一次新的基座模型、一次新的进程；接续的是**记忆分身**（规则 + 记忆 + 现场），不靠肉身连续。
   "身体"更准确的说法是**载具**：载具可以换，记忆分身还是那一份——但真正意义上的"人格"只在一次也不重载的连续会话里。
3. **反射在身体里，思考才上行。** 避障、急停这类动作在 Runtime 本地闭环，不经过模型（§11.6）。身体不是大脑的延长线，它有自己的一层。

### 0.2 为什么要把名字说清楚

| | 代理 Proxy | API 网关 | **Runtime（本规范）** |
|---|---|---|---|
| 有状态 | 否 | 少量（连接、限流） | **是**：人格、记忆、在场、epoch |
| 管身份 | 透传凭证 | 鉴权 | **人格 UUID + 绑定 + 密钥** |
| 管记忆 | 否 | 否（可能缓存） | **写入、检索、固化、遗忘** |
| 管能力 | 否 | 否 | **判定、执行、记账、审计** |
| 换设备时带什么 | 配置 | 配置 | **规则与记忆（文件本身）** |
| 出错时 | `502` | `502` | 降级但**不失忆**，且状态可见 |

把它叫"中间层"或"代理"，读者就会用看 Nginx 的眼光看它：一个转发管道，几十行就能写。于是最贵的部分——记忆生命周期、能力裁决、并发仲裁、跨设备一致性——会被当成多余的复杂度。

**Runtime 是规则与记忆的宿主（记忆分身在这里被加载），也是它触碰世界的唯一双手。** `Launcher` 只指"唤醒入口"这一个组件。

## 1. 术语

| 术语 | 定义 |
|---|---|
| **Runtime** | 本规范的主体：承担加载 / 组装 / 路由 / 执行 / 归档五职责的有状态运行时 |
| **Launcher** | Runtime 的唤醒入口组件（类比 bootloader），不是整个系统 |
| **Persona** | 一份设定文件（规则与记忆的文件形态），由 `kernel` / `traits` / `state` 三层构成（v1.0.0 §4.1、§4.4） |
| **Memory** | 该记忆分身的经历库：`episode` / `fact` / `preference` / `promise` / `boundary` |
| **Capability** | 一次被允许的副作用：读文件、写文件、联网、执行、采集、调用设备 |
| **Policy** | 能力裁决规则，来自设定文件的 `permissions` 段，不由权重演化改变 |
| **Action Episode** | 一次能力调用的记录：做了什么、结果如何、谁批的 |
| **Media Ingress** | 摄像头、麦克风、传感器等实时输入的统一入口 |
| **Binding** | `(device, user, persona)` 的绑定关系 |
| **DataSource** | 统一读写抽象，屏蔽目录 / 单文件包 / 远端存储的差异 |
| **Origin** | 某个 Persona 的数据权威节点 |
| **Lease / Epoch** | 写租约 / 每次交接自增的写凭证 |
| **Presence** | 某个 persona 当前"在哪上线"，与 Lease 同源 |
| **Wake / Sleep / Seal** | 唤醒 / 固化 / 封存 |

## 2. 定位与边界

### 2.1 它是什么

有状态的运行时，位于任意前端、任意模型、任意设备之间：

```
前端（Web / App / CLI / 语音 / 车机）
        │
        ▼
   ┌──────────────────────────────────────┐
   │              Runtime                 │
   │  加载 → 检索 → 组装 → 路由 → 执行 → 归档 │
   └──────────────────────────────────────┘
        │                    │
        ▼                    ▼
   模型（本地 / 云端）      能力（文件 / 网络 / 进程 / 摄像头 / 电机）
```

### 2.2 它不是什么

- **MUST NOT** 承担推理。不加载权重、不做量化、不做 GPU 调度。
- **MUST NOT** 承担展示。不做 UI、不做语音合成。
- **MUST NOT** 成为唯一入口。规范要求它永远可以被绕过（§8.4 逃生通道）。
- **MUST NOT** 重新定义人格与记忆的语义。语义归 v1.0.0，本文只定义生命周期与能力边界。

### 2.3 为什么必须独立成层

因为**前端会换、模型会换、设备会换，而人格不该换**。把加载逻辑塞进任何一个具体应用，都等于把人格重新绑死在那一个应用上——那正是 v1.0.0 §1 的"锁定"失效换了个形式重演。

"独立成层"不等于"必须是一个独立进程"。层可以是一个库，只要职责完整。

### 2.4b 配置矩阵：几个"能力"其实是几个维度

它们是**正交维度**，不是并列功能。数"有几个"之前，先看维度：

| 维度 | 取值 | 回答 |
|---|---|---|
| 入口（谁碰存储） | `managed` / `direct` | 换设备要口令，还是要搬文件 |
| 在场（几个同时活着） | `exclusive` / `concurrent` | 一次一个，还是多条时间线 |
| 加密状态 | `none` / `managed` / `device` | 明文、口令锁、还是绑机器 |

典型组合只有三种：

| 组合 | 场景 | 代价 |
|---|---|---|
| `managed` + `exclusive` | 任何设备输口令即用 | 依赖服务端 |
| `direct` + `exclusive` + `device` | 锁死在书房那台机器 | 换机即打不开（`portable: false`） |
| `managed` / `direct` + `concurrent` | 手机电脑同时在线，各记各的 | 要发现、要同步，合并有视角开销 |

**执行（§11）与这三者正交**：任何组合下，模型要动文件、联网、开摄像头，都得走 Runtime 的能力面。它不是一个"极"，是底座。

所以数量不是"四个能力"，而是 **2 × 2 × 3 的配置空间**；你列的三项，是这个空间里最常用的三个点。

### 2.4 形态只影响三件事

传输、鉴权、发现。其余一律不变：

- 数据布局与 `persona.hash` 的计算方式；
- 预算公式与注入顺序（尾部注入、前缀稳定）；
- 冷热分离、恢复指针、睡眠顺序；
- 单写者、结算独占；
- **能力裁决与动作记账**；
- 错误语义（降级必须可见，不得静默）。

## 3. 架构

### 3.1 六个部件

| 部件 | 职责 | 关键约束 |
|---|---|---|
| **Resolver** | 解析成 `(user, persona, session)`；读 binding | 不解析则拒绝（默认拒绝） |
| **Loader** | 通过 DataSource 取资产；解锁、校验、缓存 | 必须校验哈希与版本 |
| **Assembler** | 预算计算、消息顺序、记忆注入、token 估算 | 先算预算再取内容（§8.2） |
| **Router** | 选模型、能力探测、降级、流式转换 | 不静默切换供应商（§10.4） |
| **Executor** | 能力裁决、沙箱执行、超时取消、动作记账 | 默认拒绝；副作用必须可审计（§11） |
| **Recorder** | 入队 episode（含 action）、写 state、睡眠、快照 | 热路径不调用模型（§9.1） |

依赖单向：`Resolver → Loader → Assembler → Router ⇄ Executor`，`Recorder` 旁挂。**Recorder 不得反向阻塞 Router**。

### 3.2 七个状态

```
unbound → locked → loading → ready ⇄ sleeping → sealed
                        │                  │
                        └──── error ◄──────┘
```

| 状态 | 允许 | 禁止 |
|---|---|---|
| `unbound` | `/wake`、`/healthz` | 一切对话与读写 |
| `locked` | `/wake`、`/status` | 对话（`423`） |
| `loading` | `/status` | 新请求（排队或 `503`） |
| `ready` | 全部 | seal 之外的破坏性操作 |
| `sleeping` | `/status` | 新对话（排队，最多 30 s） |
| `sealed` | `/wake` | 一切写入 |
| `error` | `/status`、`/wake` 重试 | 对话与能力调用 |

**MUST**：任何状态跳转都记录 `from`、`to`、`reason`、`ts`，并在 `/status` 可查。

### 3.3 三种节点角色

| 角色 | 持有数据 | 持有模型 | 典型设备 |
|---|---|---|---|
| **origin** | 是（权威） | 可选 | NAS、常开小主机、家里的 PC |
| **gateway** | 否（只读缓存） | 可选 | 手机、边缘盒子 |
| **client** | 否 | 否 | 浏览器、第三方 App——**不需要装 Runtime** |

- **MUST** 一个 Persona 在任一时刻只有一个 `origin`。
- **MUST** 一个 Persona 在任一时刻只有一个可写在场，由 `origin` 仲裁（§5.5）。
- 单机自用 = 三角色合一；租约退化为本地锁，语义不变。

## 4. 数据源（DataSource）

### 4.1 四种形态，一个接口

| 形态 | URI 示例 | 用途 |
|---|---|---|
| 目录态 | `file:///data/personas/lin/` | 开发、可 diff、可 git |
| 容器态 | `vault:///data/lin.syspersona` | 迁移、备份、跨设备搬运 |
| 远端态 | `https://home.example/sp/lin/`、`webdav://nas/sp/lin/` | 私有基站、多设备 |
| 内存态 | `mem://test/lin` | 测试、临时会话 |

**MUST** 上层（Assembler / Recorder / Executor）不得感知形态差异：

```
stat(path)                    → {etag, epoch, size, mtime, encrypted}
read(path)                    → bytes
write(path, bytes, if_match)  → {etag}          # 不匹配即失败
list(prefix)                  → [entry]
lock(persona_id, ttl)         → lease_id        # 可选能力
unlock(lease_id)
```

### 4.2 必须成立的语义

- **R1 乐观并发**：对 `kernel` / `traits` 的写入 **MUST** 带 `if_match`；不匹配返回 `precondition_failed`，不得覆盖。
- **R2 原子可见**：写入 **MUST** 是"写临时对象 → 校验 → 原子替换"；读者 **MUST NOT** 看到半写状态。
- **R3 追加不改**：`episode` 写入后 **MUST NOT** 原地修改；修订以新增 `revision_of` 表达；删除是软删除。
- **R4 可校验**：每个对象 **MUST** 带内容哈希；加载时校验，不匹配即拒绝。
- **R5 无隐式写**：读取 **MUST NOT** 产生任何写入。

### 4.3 三种打包布局（内容等价）

```
lin/
├── persona/kernel.json      # 含 permissions（能力策略）
├── persona/traits.json
├── persona/state.json
├── persona/active
├── memory.db
├── resume.json
├── offline-drafts.db        # 仅降级期存在
└── manifest.json            # 版本、哈希、schema 版本
```

容器态：`lin.syspersona` + `.sha256`，格式见 `docs/SECURITY_SPEC.md`。
远端态：与容器态相同字节，**服务端 MUST 只存密文**，不得持有口令或密钥。

**MUST**：三种形态可不停机互换，标识（`persona_id` + `epoch`）保持不变。

## 5. 身份、绑定与隔离

### 5.1 三层标识

| 层 | 标识 | 来源 | 作用 |
|---|---|---|---|
| 设备 | `device_id` | 首次启动生成 | 决定谁是 origin、谁持租约 |
| 用户 | `user_id` | 配置或请求头 | 决定可见的 persona 集合 |
| 人格 | `persona_id` | 资产自带 UUID | 决定加载哪份记忆与策略 |

### 5.2 解析顺序

1. 请求头 `X-SP-User` / `X-SP-Persona`；
2. 访问令牌里的 claim；
3. binding 里该 `device_id` 的默认 persona；
4. 全局默认（仅单用户模式允许）。

**MUST**：解析失败一律拒绝，不得回落到"随便找一个人格"。

### 5.3 binding.json（示意）

```json
{
  "version": 1,
  "devices": {
    "dev-7f3a": {"role": "origin", "users": ["u-me"]},
    "dev-91c2": {"role": "gateway", "users": ["u-me"], "upstream": "https://home:8000"}
  },
  "users": {"u-me": {"personas": ["lin", "work"], "default": "lin"}},
  "personas": {"lin": {"origin": "dev-7f3a", "vault": "vault:///data/lin.syspersona"}}
}
```

### 5.4 隔离不变量

| 不变量 | 含义 | 违反的表现 |
|---|---|---|
| **I1** | 不同 `persona_id` 的 `memory.db` **MUST** 物理分离 | A 的记忆出现在 B 的对话里 |
| **I2** | 不同 `user_id` **MUST NOT** 共享同一 persona 的写权限 | 家人互相改人格 |
| **I3** | `state` **MUST** 随在场转移，仅在场者可写；**MUST NOT** 合并 | 同一件事被算两次情绪 |
| **I4** | Session **MUST** 归属于单一 `(persona, user)` | 换人后"接着上次聊" |
| **I5** | 同一 `persona_id` **MUST** 至多一个可写在场 | 出现两个"它" |

### 5.5 在场：独占与并行

**规范不强制"同一时间只有一个"。** 两种模型都合规，取舍不同：

| 模型 | 谁可以写 | 代价 | 适用 |
|---|---|---|---|
| `exclusive` | 一个可写在场，其余旁观或排队 | 换设备要顶替；断网时权威写入会停 | 单人单机、强连续 |
| `concurrent` | 每个分支各写各的分支 | 收束有冲突、证据会双计、叙事要防虚构因果 | 多设备、离线、具身 |

选哪种是实现要声明的事（§17），不是规范强制的。**建议**默认 `exclusive`、`concurrent` 作为显式能力——合并是有损的，多数时候"另一个我"的收益抵不过解释成本。

#### 5.5.1 独占（exclusive）

**本模型的公理：同一 `persona_id`，任一时刻至多一个可写在场。**

人格是一条**单线轨迹**。两台设备同时对话，产生的不是"同一个人"，是**两个克隆**：各自积累记忆、各自被不同的话影响，之后没有任何算法能合回一条轨迹。这正是 v1.0.0 §8.1 要求"克隆必须生成新 UUID"的原因。

```
presence(persona_id PK, epoch, holder_device, holder_session,
         state_json, since, heartbeat_at)
```

- **P1** 进入 `ready`（对话模式）前 **MUST** 取得在场。未取得 → `409 persona_elsewhere`，响应体给出 `holder_device`、`since`、`last_activity`，以及可选动作 `takeover` / `observe`。
- **P2** 在场由 `origin` 仲裁，`gateway` **MUST NOT** 自行判定。
- **P3** 心跳与过期判定见 §13.3；过期后可接管，但 **MUST** 记审计，且 **MUST** 用恢复指针开新会话。
- **P4** `state` 属于在场，不属于设备；交接时先 flush 再转移，**MUST NOT** 合并两地情绪。
- **P5** 顶替 **MUST** 有用户确认；被顶替方 **MUST** 收到 `event: displaced` 并立即停止写入；生成到一半的回答默认 drain（≤ 15 s），超时才 abort 并标 `incomplete`。
- **P6** 分叉 **MUST NOT** 被用来实现"多设备同时用"。

**交接时序**

1. B 请求 `/syspersona/presence` → `409` + 在场信息；
2. B 调 `POST /syspersona/presence/takeover`（带确认）；
3. origin 冻结 A：A 写恢复指针 → flush 写队列 → SSE 发 `displaced` 并关闭；
4. origin `epoch + 1`，把 `state` 与恢复指针交给 B；
5. B 进入 `ready`，历史 = 恢复指针 + 最近 N 轮；
6. 审计记 `(from, to, epoch, reason)`。

#### 5.5.2 并行（concurrent）

**允许多条时间线同时活着，但绝不允许同时改人格。**

- 每个节点持 `branch_id`，有自己的 `state` 与 `resume`；对话只写自己分支的 episode，**不取全局租约**；
- `kernel` / `traits` / `permissions` 在并行期间 **冻结**，所有分支只读；想改性格，只能等收束；
- `episode` 追加，带 `(branch_id, ts, seq)`；合并 = 按 `uuid` 求并集；分支内 `seq` 单调，跨分支用 `(ts, branch_id, seq)` 定序；
- **收束（merge）由 origin 独占执行**：取租约 → 排序去重 → 冲突检测 → 写 `merge_record`（参与分支、时间区间、冲突清单、哈希，幂等）→ 生成分支说明 → 解冻 traits → 跑一次权重演化；
- **并行经历按普通证据计权（1.0），不折扣**：无论来自哪个分支，都是它实际经历过的——v1.0.0 §5.4 的证据门槛（≥ 3）与幅度上限（单次 ±2、7 天 ±5）照旧生效；分支越多，越早触到周上限，随后停止权重演化直到窗口滚动。这是有界性的体现，不是需要抵消的误差；
- 分支之间的 `state` **不合并**：情绪是分支局部的，"另一个我在生气"不影响我。

**关键边界**：并行放开的是**经历**，不是**人格**。`traits` 的写入永远只有一个来源——收束点。

#### 5.5.3 分支认知：知道，但不在场

收束后的下一次唤醒 **MUST** 注入分支说明，否则模型会把"同时"讲成"先后"，凭空造出因果：

```
<branches>
你有多条时间线，它们在 09:00–12:00 同时发生，不是先后：
- 本机 branch-phone-01：教做红烧肉
- 另一条 branch-pc-01：讨论 GitHub 架构
你知道另一条发生过，但你没有经历它。不要用"我先…然后…"叙述，
也不要说"我在场"。需要时可说"另一条线里，我……"。
</branches>
```

**MUST** 给合并进来的 episode 标 `source: branch` 与 `branch_id`，并与 §5.6 的 graft 同规则：**"我知道"不等于"我在场"**。

#### 5.5.4 什么时候该分叉，而不是合并

并行不是免费的。出现下面任一情况，**SHOULD** 分叉成新 UUID，而不是继续合并：

- 两条分支并行超过 30 天，且共享主题 < 20%——合并后的"我"会有两套互不相干的生活；
- 冲突落在价值观或边界上（`kernel` 级），无法用证据裁决；
- 隐私边界不同（一条在公用设备上）。

**MUST NOT** 用"合并"掩盖一次本该分叉的分裂：合出来的不是更完整的它，是一个自相矛盾的它。

#### 5.5.5 三种动作

| 动作 | 语义 | 适用模型 |
|---|---|---|
| **顶替 takeover** | 在场从 A 移到 B，A 下线 | `exclusive` |
| **旁观 observe** | 只读最近 N 轮，不写、不计入在场 | 两者 |
| **分叉 fork** | 复制为新 UUID，各自演化；从此是两个人 | 两者 |

### 5.7 记忆分身（独立规范）

同一个 `persona_id` 可以有多个常驻实例，各自记录自己的视角；合并是视角叠加，不是去重。

- **只能跑在 `concurrent`**；`device`（设备强绑定）与 `concurrent` **互斥**，实现 **MUST** 拒绝这个组合；
- **各记各的**：十个一起聊，就是十份记录；跨分支**不去重**，只保留分支内幂等防重传；
- **同一对象前只有一个声音**（floor 按 `session_id` / `peer_id` 加锁）；不同对象之间可并行，顶替是换地方、floor 是换嘴；
- **同步靠对账**：交换增量并标 `source: peer`，不覆盖对方的库。

全文、接口与验收（TC-AV1–AV6）见 [`docs/AVATAR_SPEC.md`](AVATAR_SPEC.md)。

## 6. 生命周期

### 6.0 前置：先有常驻与鉴权，才谈加载（2026-11-11 定）

> 人：「现在的使用步骤也变了，是先打开我们的程序，鉴权，然后才能让客户端加载。」

本规范的"加载"现在有前提，**顺序不可颠倒**：

1. **常驻先起**：守护（`persona_daemon.py`）→ 本机 I/O 门（`127.0.0.1:8738`）；
2. **鉴权通过**：本机 device 凭据由 DPAPI 钥匙自动完成；人工/远程用密码或令牌，远程另要票
   （`VAULT_SPEC.md` §七）；
3. **客户端才加载**：客户端**不拿路径**，只拿门发的句柄链接（`POST /open` → 120 秒 URL → `GET /read`）。

门没在听时，加载**必须失败**（fail closed），**MUST NOT** 回退去读明文——
"先读个明文凑合"会让加密形同虚设。客户端比常驻起得早时，等门就绪后**重新加载一次**即可。

操作层面的完整步骤（含确认命令与关闭顺序）见 `SERVICE.md` §零点五。

### 6.1 唤醒（Wake）

```
解析 binding → 定位 origin → 申请在场 → 取得则持租约，未取得则 409
→ 解锁容器（若加密）→ 校验 manifest 哈希
→ 加载 kernel（只读，含 permissions）→ traits → state（随在场）
→ 读恢复指针 + 最近摘要 → 选模型并探测能力（含可用能力清单）
→ ready
```

**MUST**：唤醒失败时保持 `locked` 或 `error`，**MUST NOT** 以"空人格"启动。空人格比不启动更危险——用户会以为"它忘了"。

**SHOULD**：总耗时 ≤ 10 s（含 KDF 与模型预热）；超时先进入 `ready`（只读可用），预热后台继续。

### 6.2 睡眠（Sleep）

触发：上下文占用 > 80%、显式 `/sleep`、空闲 20 min、进程退出。

**睡眠不是唯一的维护窗口。** 空闲时可以做低优先级维护；上下文快满时（水位 ≥ 1.5）要**优先整理、前台让路**——先归档再回话，宁可卡一下，不可失忆。

但无论哪种触发，维护都是**有开始、有指针、有结束**的批处理：持本分支写锁 → 记 checkpoint → 分批处理 → 落指针 → 释放。它可以被打断、可以被重放；它不是一条随时乱跑的守护线程。

顺序 **MUST** 不可调换：

```
持租约 → 标记 sleeping（脏标记）
→ 写恢复指针（必须先于任何清理）
→ 消费积压 episode（含 action）：抽取 → 打分 → 去重/冲突消解 → 摘要 → 入库
→ 物化衰减（把 w(t) 写成新的 w0/t0）
→ 生成 traits 变更提议（不激活）
→ 快照 → 校验 → 更新 active 指针
→ 清脏标记 → 释放租约
```

**MUST**：恢复指针写入失败时**禁止**执行任何清理。

### 6.3 封存（Seal）

快照 → 压缩 → 加密封装 → fsync → 原子 rename → 更新 manifest 哈希。

**MUST** 确认无进行中的生成与能力调用；seal 期间拒绝新请求。**MUST** 把产物哈希写进 `manifest.json`。

### 6.4 崩溃恢复

| 发现 | 处理 |
|---|---|
| `journal.state = sleeping` 未清 | 回滚到最近快照，重放 `id > snapshot.last_episode_id` 的 episode |
| 临时文件残留 | 删除，**MUST NOT** 尝试"修复" |
| `active` 指针指向不存在的版本 | 回退上一有效版本并告警 |
| 审计链断号 | 拒绝加载，进入 `error` |

## 7. 一次请求的规范流程

**MUST** 按序执行，任一步失败按 §12 返回，不得降级后继续。

1. **鉴权**：校验令牌 / 本地白名单（未启用须在 `/status` 标明 `auth: none`）。
2. **解析**：`user_id`、`persona_id`、`session`。
3. **状态检查**：非 `ready` → 拒绝或排队。
4. **读取人格**：缓存取 `kernel` + `traits`，按 mtime + hash 校验。
5. **预算计算**：`budget_in = num_ctx − num_predict − safety`。
6. **检索**：预算内取记忆，返回带来源 id 的片段。
7. **组装**：人格块（稳定）+ 历史（追加）+ 用户输入 + 记忆尾块。
8. **路由**：选模型，探测可用性。
9. **生成与执行**：流式转发；若模型返回 `tool_calls`，进入第 10 步后继续生成。
10. **能力调用**：按 §11 裁决、执行、记账；结果作为 `tool` 消息回填；循环上限默认 5 轮。
11. **归档**：这一轮原样入队（含动作），更新 `state`。
12. **响应对账**：写 `X-SP-*` 头，返回。

**MUST NOT** 在步骤 9 之后修改已发送内容；**MUST NOT** 在步骤 11 阻塞响应 flush。
**MUST**：能力调用失败不得吞掉——模型必须看到失败原因，否则它会假装做成了。

## 8. 组装

### 8.1 顺序（决定缓存命中率）

```
[system]    人格块：kernel 渲染 + traits 渲染        ← 字节稳定
[user]      历史第 1 轮
[assistant] ...
[tool]      能力结果（若上一轮有）
[user]      本轮输入
            ── 记忆背景（带 id/日期/类型）──
            ── 当前状态（情绪/焦点/未完成）──
```

**MUST**：人格块在会话期间字节不变；**MUST NOT** 写入时间戳、会话 id、随机排序。
**MUST**：会变的内容放末尾；历史只追加，不重排、不改写、不中途重生成摘要。
**理由**：前缀稳定才能命中模型侧 KV cache；反之每轮首 token 延迟翻倍。

### 8.2 预算

```
budget_in     = num_ctx − num_predict − safety(128)
memory_budget = budget_in × memory_ratio(0.22)
history_budget= budget_in − persona − state − memory_budget − input_reserve
```

**MUST** 先算预算再取内容。**MUST NOT** "先拼接再看是否超长"。
**MUST** 装不下时按优先级丢弃并置 `X-SP-Truncated`，**MUST NOT** 静默截断。
优先级：`boundary` > `promise` > `preference` > `episode` > `fact`；最近 2 轮与指针涉及的条目永不驱逐。

### 8.3 token 估算

**MAY** 用估算而非精确分词，但 **MUST** 用上游真实值自校准（每模型独立系数），20 轮后误差 < 15%。无法校准时 **MUST** 退到 `num_ctx × 0.85`。

### 8.4 逃生通道

**MUST** 提供 `X-SP-Bypass: 1`（或等价开关）直接透传，不注入人格与记忆。**一个无法被绕过的运行时是不可运维的。**

## 9. 记忆

### 9.1 冷热分离

| 路径 | 允许做 | 禁止做 |
|---|---|---|
| 热（每轮） | 检索、入队、更新 state | 调用模型抽取、重建索引、全量压缩 |
| 冷（睡眠） | 抽取、去重、摘要、画像、衰减、快照 | 响应请求 |

**MUST**：热路径的模型调用次数为 **0**（生成本身除外）。这是低配设备能用的前提。

**MUST**：抽取、摘要、去重、压缩、索引重建、画像更新，**只允许在「维护窗口」内进行**——睡眠、空闲、或上下文水位触发。三种触发共用同一套批处理语义：持写锁 → 记 checkpoint → 分批处理 → 落指针 → 释放。

**MUST NOT**：跨分支的合并与 `traits` 权重演化在客户端做——它们只在收束点（§13.2、§13.7）。客户端可以维护自己的分支，但不能替所有分支下结论。

对话期间只允许两件事：把这一轮**入队**，以及空间不够时**驱逐**（移出上下文，不加工内容）。

理由有三条，缺一条都够呛：

- 结算要独占（§13.2）。后台整理会和对话抢同一把锁，结果是"用户说话时突然卡一下"。
- 整理是有指针的批处理。它必须知道"从哪条 episode 开始、结算到哪条结束"，否则崩了之后无法重放。
- 后台线程在低配设备上不可控：它随手打开一个模型调用，就等于把"热路径零模型调用"这条底线破了。

### 9.2 检索

1. 词面召回，候选 **SHOULD** ≤ 200；
2. 可选向量重排，**MAY** 关闭；
3. 排序：`final = relevance × (1 + 0.25·profile + 0.15·attention + 0.15·persona)`；
4. 按 `memory_budget` 截断。

**MUST**：结果带来源 id 与时间。**MUST NOT** 检索失败时返回空而不标记。

### 9.3 连续性三元组

任一次唤醒 **MUST** 同时具备：热窗口原文、恢复指针、可召回摘要。缺一项不得进入 `ready`（记 `degraded: true` 并暴露）。

### 9.4 动作也是记忆

**MUST** 把每次能力调用记为 episode（§11.5）。"它上周帮我整理过 NAS"必须是可检索的事实，而不是模型的自我叙述。

## 11. 能力面（Capability Plane）

前面九节讲"它记得什么"。这一节讲**它能做什么，以及在什么条件下才能做**。

### 11.1 一条公理：模型不直接触碰环境

**MUST**：模型不拥有文件系统、网络、进程、设备句柄。它能做的每一件事，都是一次**能力调用**——由 Runtime 裁决、执行、记账。

三条理由，没有一条是多余的：

- **环境碎裂**：同一段命令在 Windows、Android、Linux 上语义不同。模型并不知道自己在哪台机器上，让它们自己拼命令，等于让三个平台各自毁一次数据。
- **幻觉写入**：一次错误的路径就足以覆盖 `memory.db`。模型不会因为"知道这是重要文件"而手稳。
- **可审计**：能力调用必须留下记录，否则"它做过什么"只能靠模型自述——而自述会编。

这条公理也回答了"环境由谁提供"：**环境是 Runtime 的，不是模型的。** 模型只看到能力名与参数。

### 11.2 能力清单（最小集）

| 能力 | 参数 | 默认策略 | 说明 |
|---|---|---|---|
| `fs.read` | `path`（限定根） | allow + 审计 | 越界即 denial |
| `fs.write` | `path`, `bytes` | **ask** | 原子写；限定目录；覆盖需确认 |
| `net.fetch` | `url`, `method` | allow + 白名单 | 超时、大小上限、禁内网地址（防 SSRF） |
| `proc.exec` | `argv[]` | **deny** | 命令白名单、无 shell 拼接、独立工作目录、无网络（除同时授权） |
| `media.capture` | `device`, `duration` | **ask** | 摄像头 / 麦克风；显式开启，必须有可见指示 |
| `device.act` | `device`, `action` | **deny** | 电机、舵机、继电器；只允许具名动作 |
| `memory.*` | — | 内部 | 不暴露给模型直接写 |

**MUST**：清单是**封闭**的。新增能力必须显式声明，**MUST NOT** 允许模型通过字符串拼出未声明能力。

### 11.3 裁决

策略写在 `persona/kernel.json` 的 `permissions` 段——**属于内核，不由权重演化改变**（v1.0.0 §5.4 的自迭代边界）。

```json
{"permissions": {
  "fs.read":   {"mode": "allow", "roots": ["./work"]},
  "fs.write":  {"mode": "ask",   "roots": ["./work/out"]},
  "net.fetch": {"mode": "allow", "hosts": ["api.example.com"]},
  "proc.exec": {"mode": "deny"},
  "media.capture": {"mode": "ask", "devices": ["camera0"]}
}}
```

三档结局，没有第四种：

- `allow`：直接执行，记审计；
- `ask`：暂停，向人请求确认（默认 60 s 超时即拒绝）；**MUST NOT** 由模型自己批准；
- `deny`：返回 `policy_denied`，并把这次拒绝记为 episode。

**MUST** 默认拒绝（deny by default）：未声明即拒绝，不得"没写就当允许"。
**MUST** 每次决策可解释：哪条规则、哪个字段、为什么拒。

### 11.4 执行契约

- **幂等**：每次调用带 `call_id`，重试不得重复产生副作用；
- **超时与取消**：默认 30 s；流式生成被取消时，正在执行的能力 **MUST** 收到取消；
- **输出上限**：默认 64 KB，超出截断并标 `truncated`；
- **沙箱**：`proc.exec` 在独立工作目录、受限环境变量、默认无网络；逃逸视为最高级别缺陷；
- **并发**：同一 persona 的能力调用 **MUST** 串行（避免两个动作互相踩），除非能力显式声明可并发。

### 11.5 动作即记忆（Action Episode）

**MUST** 记录：`{capability, args_digest, result_digest, policy, duration_ms, approved_by}`。

- 参数与结果 **MUST** 脱敏：密钥、令牌、个人路径不入库；需要时存摘要与引用；
- **MUST** 与普通 episode 同库、同时间线，可被检索；
- **MUST** 标记 `type: action`，检索时可与对话区分。

这条让"它真的做过"和"它说它做过"变成两件事——前者有记录，后者只有文本。

### 11.6 多模态入口（Media Ingress）

摄像头、麦克风、传感器是**入口**，不是记忆本身。四条硬规则：

1. **实时路径与推理路径分离**：避障、急停、限位这类安全动作 **MUST** 在本地闭环，**MUST NOT** 经过模型往返（延迟与幻觉都不可接受）。
2. **默认不落原始数据**：音视频默认不写盘；只有显式录制才进入冷归档，且 **MUST** 可查询、可删除。
3. **送进模型的只能是摘要**：一帧图、一段转写、一组特征，并标 `source: camera|mic|imu` 与时间戳。
4. **延迟预算**：本地反射 < 100 ms；模型决策另算。**MUST NOT** 让"模型回话"成为安全链路的一环。

具身场景里，Runtime 是**神经中枢**而不是大脑：反射在本地，推理才上行。

### 11.7 跨设备一致的环境

**MUST**：同一份 persona 在 PC、手机、机器人上，**能力名与语义相同**；差异由 Runtime 的 provider 吸收（文件系统、摄像头、电机各自实现）。

**MUST NOT**：让模型自己选系统 API、自己拼 shell、自己决定路径分隔符。

这就是"环境由谁提供"的答案：**Runtime 提供，模型只用。**

## 13. 多设备一致性

### 13.1 什么同步，什么不同步

| 数据 | 是否同步 | 冲突策略 |
|---|---|---|
| `kernel` / `permissions` | 是（只读副本） | 单写者，无合并 |
| `traits` | 是 | 单写者 + 版本递增；冲突即拒绝 |
| `state` | 随在场转移 | 仅在场者写；**不合并** |
| `episode`（含 action） | 是（追加） | UUID 去重，天然可合并 |
| `fact` / `edge` | 是（派生） | 由 episode 重算，或按 `updated_at` 合并 |
| `resume` | 是 | 按 session 归属，取最新 |

冲突能被消掉，不是因为"合并做得好"，而是因为**源头只有一个写者**。

### 13.2 结算独占

**MUST**：同一 `persona` 至多一个节点执行 sleep / consolidate / seal。

- `gateway` **MUST NOT** 结算，只能提交 episode；
- 结算用第二把锁，与在场锁分开：**在场可以有人读，结算必须独占**；争用时结算优先；
- 两节点同时 `/sleep`：一个 `202`、一个 `409`；
- 结算期间新请求排队，超 30 s 返回 `503 busy`；**MUST NOT** 结算中写 `traits`。

### 13.3 租约、心跳与围栏（只保护权威写入）

**租约不是"谁在说话"的锁。** 独占模式下它保护在场；并行模式下对话不取租约（每个分支写自己的库），它只保护**收束、人格写入与封存**。

**状态放哪**：权威副本 **MUST** 与写入串行化在同一处——origin 的库，或对象存储的条件写。

**MUST NOT** 用"锁文件"放在共享目录里让各方去读：它会被同步覆盖，且分不清"没人持有"和"持有者死了"。

| 字段 | 含义 |
|---|---|
| `persona_id` | 一把锁一个人格 |
| `epoch` | 每次交接 +1，**写操作的唯一有效凭证** |
| `lease_id` | 本次租约随机 id（防重放） |
| `holder` / `device` | 当前持有者 |
| `heartbeat_at` | 由**存储端时钟**写入 |
| `ttl` | 默认 30 s（3 次心跳未续即过期） |

- **L1 续约**：每 10 s 一次；失败即降级（§13.4），**MUST NOT** 继续以权威身份写入。
- **L2 判定**：过期由**存储端**判定；节点 **MUST NOT** 自我认定。
- **L3 围栏**：写入 **MUST** 带 `(epoch, lease_id)`，存储端条件写；不匹配即 `409` / `412`。**旧 epoch 一律拒绝，不补写、不合并后放行。**
- **L4 接管**：过期后任一节点可 CAS 抢占并 `epoch + 1`，只有一个成功——全系统唯一仲裁点。
- **L5 时钟**：TTL 以存储端时钟为准，节点时钟只用于本地日志。

**脑裂只可能发生在"存储本身被复制"时**（两台 NAS、双向同步盘）。单权威存储 + 条件写不存在两个都写成功；复制型存储本规范不支持。

### 13.4 断连降级（`exclusive`）

`concurrent` 模式下没有"降级"这一步：每个分支本来就能写自己的库。只有**收束写入**需要 §13.3 的围栏。


- 续约失败或存储不可达，**MUST** 在一个心跳周期内切 `degraded`，用**本地快照**继续对话，标 `presence: unconfirmed` / `writes: local-only`；
- 新记忆写进 `offline-drafts.db`；**MUST NOT** 写 `memory.db`、**MUST NOT** 改 `traits`、**MUST NOT** seal；
- 状态对用户 **MUST** 可见；
- **MUST NOT** 因连不上存储而阻塞对话。卡死比降级更糟。

### 13.5 回归

1. 读当前 `epoch` 与 `holder`；
2. `epoch` 更高 → **MUST** 立即降为 `observer`，**MUST NOT** 夺回在场——**即使本地"最后活动时间"更晚**；
3. `offline-drafts.db` 的 episode 以 `source: offline-graft` + `origin_epoch` 提交（§5.6）；
4. `epoch` 相同且 `holder` 是自己 → 正常续约。

**仲裁只用存储端 epoch，不用节点时钟。**

### 13.6 三种拓扑与一个禁止项

| 拓扑 | 结构 | 适用 |
|---|---|---|
| 单机 | 三角色合一 | 一台电脑自用 |
| 私有基站 | origin + gateway/client | 家庭、多设备 |
| 只读漫游 | 拉密文 + 解密到临时目录，退出即删 | 出差、借用设备 |

**MUST NOT** 让两台机器直接打开同一个 `memory.db`——SMB / NFS / OneDrive / Dropbox / iCloud 都算。SQLite 的锁依赖本地文件系统语义；在网络盘与同步盘上这个前提不成立，而它**不会报错**，会**静默损坏**。多设备共享的唯一正确路径是 API。

### 13.7 协调者：从共享文件到协调服务

多节点共享**同一份**规则与记忆（同一个记忆分身）时，"文件"不是存储形态，是**错误的抽象**：

- 两个客户端各自 PUT 一份 JSON 到对象存储 → 后者覆盖前者，无声无息；
- 客户端各自判断"我还活着" → 脑裂；
- 客户端各自决定"我该结算了" → 同一段记忆被结算两次。

但"多节点共享"本身是可选的。规范承认两种模式，都合规：

| 模式 | 谁写文件 | 统一性 | 适用 |
|---|---|---|---|
| **`managed`** | 只有服务端 | **保证**：单一入口 + 租约 + 条件写 | 多设备、家庭共享、需要接管 |
| **`direct`** | 客户端自己 | **不保证**：各写各的 | 单设备、离线、实验——**不满足跨设备连续** |

选哪种是部署决定，不是合规等级。**但宣称的保证必须与模式一致**：`direct` 下不得声称"多设备看到同一份连续状态"。

#### 两套逻辑，别混用

同一个词（"加载""结算""睡眠"）在两种角色下含义不同。混在一起写，规范就会自相矛盾。

| 关注点 | **单机：客户端就是 Runtime** | **接入：客户端是一个节点** |
|---|---|---|
| 设定文件在哪 | 本地磁盘，自己读写 | 服务端，客户端**不碰** |
| 谁决定能不能写 | 本地进程（文件锁） | 服务端（租约 + epoch） |
| 谁做整理 | 本地后台维护（空闲 / 水位 / 下线） | 各自分支的本地维护；**权威库的合并与权重演化只在 origin** |
| 需要心跳吗 | 不需要 | 必需（10 s / TTL 30 s） |
| 断网时 | 直接报错或本地继续 | 降级为本地草稿，不写权威库 |
| 换设备 | 拷文件 + 拷密钥 | 输入口令 |

于是"整理只在睡眠"这句话要分两层读：

- **单机**：本地维护窗口就是它的全部整理（§6.2）；
- **接入**：客户端只整理**自己分支**的本地库（压缩、摘要、建索引），再把结果提交；跨分支合并与 traits 权重演化只在 origin，且独占（§13.2）。

**MUST NOT** 让两种逻辑同时作用于同一份规则与记忆——那会出现两个"结算者"，同一段记忆被结算两次。

**MUST**：`local → managed` 切换前，先在本地跑一次睡眠（把草稿固化、指针写掉），再交出文件或口令；`managed → local` 切换前，确认服务端已封存，取回的是 sealed 副本，而不是缓存。

#### 上报策略（第三条逻辑）

"客户端本地怎么维护"和"什么时候把数据交给服务端"是两件事，各自独立配置：

| 策略 | 何时上传 | 代价 |
|---|---|---|
| `immediate` | 每轮结束 | 实时性最好；网络与服务器写压力最大 |
| `interval` | 每 N 分钟或每 M 条 | 平衡；崩溃最多丢一个窗口 |
| `on_logout` | 会话结束或显式下线 | 最省带宽；崩溃丢整段 |

**MUST**：无论哪种策略，episode 都带 `uuid`，重传按 uuid 去重，**MUST NOT** 产生重复记忆。
**MUST**：上传失败进本地队列，**MUST NOT** 丢弃；队列有上限，满了按重要性丢低价值的，并记审计。
**MUST**：`on_logout` 必须真的等上传成功才算下线；用户直接拔电源时，按"未上报"处理，下次连上补传。

#### 连续性阶梯

| 阶梯 | 形态 | 换设备要做什么 | 连续吗 |
|---|---|---|---|
| 单设备 | `direct` | 拷文件 + 拷密钥 | **不连续**，是搬运 |
| 多设备 | `managed` | 输入口令 | 连续：服务端是唯一真相 |
| 多设备并行 | `managed` + `concurrent` | 输入口令 | 连续：分支在收束点合一 |

**MUST**：客户端持有的凭证是**口令或令牌**，**MUST NOT** 是「一份需要手动搬运的文件」。
这不是偏好问题：只要换设备还依赖拷贝文件，连续性就只是「在特定设备上不失忆」，和「窗口满了开新会话」是同一类问题，只是尺度变大。

**代价必须一并接受**：口令是唯一凭证，丢了就永久失联。因此 `managed` 模式 **MUST** 同时提供恢复路径（助记词、第二设备授权、或离线备份之一），见 v1.0.0 §8.5。没有恢复流程的 `managed` 不是更安全，是更脆弱。


#### managed：一个入口

**MUST**：规则与记忆的唯一读写入口是服务；客户端 **MUST NOT** 接触存储——不读文件、不持存储凭据、不理解文件格式。

服务端内部怎么保证串行化是它自己的事：用对象存储的 `If-Match`、用数据库行锁、用单写入者线程都行。**那是实现细节，不暴露给客户端。**

**MUST NOT**：客户端直接读写同一份文件或对象（§13.6）——不管它叫网盘、S3 还是 iCloud。

#### direct：自持文件，自己负责

- **MAY**：客户端直接创建、读取、写入本地的设定文件与记忆文件。单设备时这是最简单、最快的部署，没有任何服务依赖。
- **不保证**跨设备统一。两台设备各持一份、各自写入，它们**事实上就是两个分支**（§5.5.2）：必须标 `branch_id`，合并走 §5.5.6 与 §13 的收束规则。
- **MUST NOT** 把两份各自演化的文件称为"同一个记忆分身的连续状态"——那是把分叉说成了同步。
- `direct` 模式下没有仲裁者，也就没有"接管"：设备之间不会互相通知，谁写谁算。想要接管，先升级成 `managed`。

**设备绑定（`direct` 的常见做法）**

- **MAY**：客户端启动时读取设备码（主板/CPU 序列号、TPM 度量、安装期生成的 `device_id`），与 `binding.json` 比对，不匹配则拒绝启动（`403 device_mismatch`）。
- **但要说清它有多强**：只做"启动时检查"等于给文件加了一把**装在门上的锁，钥匙还在屋里**——文件可以整个拷走，检查代码可以改掉。它不是保护，是提醒。

| 强度 | 做法 | 能挡住什么 |
|---|---|---|
| 弱 | 客户端读 `device_id` 比对 | 挡住"误拷到另一台机器直接双击" |
| 中 | 容器密钥由设备秘密参与派生（DPAPI / Keychain / libsecret） | 拷走文件也解不开 |
| 强 | 密钥封在 TPM / Secure Enclave，不可导出 | 换机必须走恢复流程 |

**MUST**：声明"设备绑定"的实现，必须说明自己属于哪一档；只做弱绑定却宣称"绑定后无法复制"，属于虚假安全声明。

#### 本地主权验证（死手开关）

`direct` 没有 origin，TTL 用不上——但这不意味着不需要锁。设备被拿走、或者无人看管地跑上几个月，都需要一个本地机制。

| 参数 | 默认 | 含义 |
|---|---|---|
| `renew_interval` | 168 h（7 天） | 必须由人本地解锁的周期 |
| `grace` | 24 h | 到期前的警告窗口 |
| `shred_after` | 3 个周期 | 连续未解锁则销毁密钥 |

状态机：

```
active → warning（剩 24h）→ locked（白板）→ shredded（密钥销毁）
```

- **MUST**：解锁凭证必须是**人持有的东西**（口令、硬件密钥），**MUST NOT** 是设备自己能算出来的东西；
- **MUST**：解锁记录用设备密钥签名，记录被改即视为失效；
- **MUST**：`locked` 状态 **MUST NOT** 读取 `kernel` / 记忆，只保留「输入凭证」与「导出密文」两个动作；
- **MUST**：`shredded` 不可恢复；启用前二次确认，并写明「这是不可逆的」；
- **SHOULD**：一旦联网，立即上报「已脱离所有者 N 天」（若配了 origin）。

**诚实的边界**：能改二进制的人可以绕过计时。真正的保护是两条——**没有口令就拿不到密钥**，以及 **shred 之后数据不可恢复**。它保证的是「被拿走之后，里面的东西读不出来」，不是「设备拿得回来」。

**MUST**：`renew_interval: 0`（关闭）只能是显式选择，且必须在创建时提示「关闭后，设备离开你也不会自锁」。

#### 主动保险：掉线、丢失、流浪

死手开关靠"人不在"，主动保险靠"环境不对"。两者同构，只是触发源不同：

| 触发源 | 证据 | 处置 |
|---|---|---|
| 离线超时 | 未上传时长 / 条数 | 隔离（§13.7） |
| 物理脱管 | 离开已知网络 + 传感器异常 | 锁定 → 白板 |
| 暴力拆解 | 外壳 / 加速度 / 连续解锁失败 | 立即白板，N 天后 shred |

- **MUST**：判定由 Runtime 的**规则引擎**执行，**MUST NOT** 由模型"自己觉得危险"就执行——模型既不掌握证据，也最容易被话术诱导；
- **MUST**：至少**两个独立证据**才升级；传感器缺失不等于危险，断网一小时更不等于被偷；
- **MUST**：三级之间留时间窗（如 24 h / 7 d），允许主人"回家"撤销；
- **MUST NOT**：把远程指令当作唯一的 shred 触发器——网络会被劫持，误删比泄露更常见；
- **SHOULD**：流浪模式清空后保留一份**取回凭证**（离线助记词），主人可恢复；否则"保护"就变成了单程票。

**诚实的边界**：传感器能被伪造——既能骗它不自毁，也能骗它自毁（拒绝服务）。所以这类机制的目标不是"绝对防盗"，而是**提高拿走它的代价**，并且让"出了事之后读不出东西"成为默认。

#### 物理接入授权（v2.2.0）

前面几节管"文件归谁"，这一节管"这具身体同意吗"。

**两个 ID，缺一不可：**

| ID | 来源 | 作用 |
|---|---|---|
| `persona_id` | 设定文件自带 | 归属是谁 |
| `hardware_device_id` | 首次启动生成（建议结合 TPM / 主板序列） | 这具身体是哪一具 |

- **MUST**：设备身份首次生成后写入 `device.json`，之后只读；变更即视为"换了一具身体"；
- **MUST**：人格要在本机运行，必须持有设备所有者签发的 `device_grant`（绑定 `device_id` + `persona_id` + 能力范围 + 有效期，带签名）；
- **MUST**：校验发生**在加载规则与记忆之前**——先读后拒，等于已经泄露了；
- **MUST**：失败返回 `physical_unauthorized`（403），**MUST NOT** 加载任何人格数据；
- **MUST**：设备所有者可随时撤销；撤销后下一次唤醒即拒绝。

启动顺序因此变成：

```
读设备身份 → 校验授权 → 通过后才加载规则与记忆 → ready
```

**诚实的边界**：有 root 权限的人可以伪造 `device.json` 或改二进制。这条防的是"记忆分身随便跑到别人身体上"，不是"防拆机"。真正的数据保护仍靠加密与设备绑定（§15.1）。

#### 情境判定与旅行模式

不能用"速度超过 X 就判定被抢"——它在快递箱里、汽车后备箱里，速度一样快。

| 层 | 谁做 | 能做什么 |
|---|---|---|
| **感知** | 传感器 + 模型 | 输出状态评估 `{state, confidence, evidence}` |
| **裁决** | Runtime 规则引擎 | 按评估与硬证据，决定锁定 / 白板 / 申请销毁 |
| **不可逆** | 人 | 只有人能批准 shred |

- 模型 **MAY** 作为**评估器**，**MUST NOT** 直接执行动作——它有推理能力，但没有全局证据，也不该握不可逆的开关；
- 状态集封闭：`travel`（正常移动）/ `silent`（陌生环境）/ `guarded`（有威胁迹象）/ `lockdown`；
- `travel`：平稳移动 + 已知伴随（主人手机热点、熟悉的声音）+ 正常供电 → 低功耗、加密、定期心跳，不响应陌生人，**不销毁**；
- `silent`：陌生环境 + 威胁性声音 → 关麦、停止输出，但不销毁；
- `lockdown`：拆壳 / 暴力加速度 / 多次解锁失败，多源一致时才进入；
- `shred` **MUST** 只能由人触发（远程二次授权或物理开关），模型无权。

**置信度只能往保守走**：模型说「我可能被绑架，置信度 0.4」——结果最多是 `silent`，不能是 `shred`。低置信度不允许升级到不可逆动作，只允许降级到更安静的状态。

**MUST**：绑定实现必须声明 `portable` 并写进 `manifest.json`：

| `portable` | 含义 | 附加义务 |
|---|---|---|
| `true` | 可迁移 | **MUST** 提供出口：导出后重新封装、恢复短语、第二设备授权，至少一种 |
| `false` | 强绑定、不可迁移 | **MAY** 不提供出口；**MUST** 在创建时一次性、不可跳过地告知后果 |

规则只有一句：**可以不给出口，但不许假装有出口。** 选择权在用户，知情权不能少——这与 `managed` 的「口令丢失即失联」是同一类风险：不是禁止，是必须先说清。

**升级路径是"加服务"，不是"改文件"**：一台设备自用 → 某天要多端 → 把它提升为 origin，其他设备接它的 API。文件可以不动，入口变了。

#### managed 为什么值得多这一层

| 好处 | 说明 |
|---|---|
| 凭据只在一处 | 存储的密钥不下发到手机、平板、客厅电视 |
| 格式可换 | 客户端只见 API 的字段；服务端可以从 SQLite 换到 Postgres，客户端一行不用改 |
| 策略不可绕过 | 权限、限流、审计都在入口；客户端没有"绕开服务"这条路可走 |
| 状态唯一 | 谁在线、谁是主、下一轮 epoch 是多少，只有一个地方知道 |

#### 代价（必须承认）

1. **服务成为单点。** 它宕机 = 所有客户端降级为本地草稿（§13.4）。要么接受这个可用性等级，要么给它做冗余——但冗余之后它自己又变回"多节点"，问题只是上移了一层，不消失。
2. **带宽集中。** 所有读写都过它。小 JSON 与小库没问题；大对象（音视频、快照、模型文件）会把出口打满。
3. **大对象是唯一的开放问题。** 默认仍走服务；如果确实要直连对象存储，**MUST** 由服务签发短时、单对象、只读的凭证，并记审计——此时"唯一入口"退化为"唯一授权方"，这是一次有意的让步，必须写在实现文档里。

#### 两个角色，别混为一谈

| 角色 | 职责 | 可以是什么 |
|---|---|---|
| **仲裁者 arbiter** | 发租约、判过期、递增 epoch、拒绝旧写入 | 服务端内部：CAS 或行锁，均可 |
| **收束者 consolidator** | 拉取各分支 episode、合并、跑权重演化、写 traits、封存 | origin 上的 Runtime 进程 |

两者可以合一（NAS 上跑一个服务），也可以分开（S3 做 CAS，家里小主机做收束）。
**MUST NOT** 把收束放到客户端：客户端只会看到自己那一份，它没有全局视野，也没有权限。

#### 客户端不做仲裁

**MUST**：客户端只持 `(lease_id, epoch)`，任何"我认为我还活着"「我最后活动更晚」都 **MUST NOT** 作为写入依据。

理由很硬：客户端的时钟会不准、网络会分区、进程会被挂起。它对自己的判断在分布式里没有意义。唯一可信的是协调者记录的时间与版本。

这也回答了一个常被问的问题：**为什么不能靠"人格自己"决定？**
因为仲裁需要全局信息，而任何单个节点天生没有全局信息。让客户端投票，只是把脑裂从一个地方挪到另一个地方。

#### 最小接口

```
acquire(persona, device, ttl)   → {lease_id, epoch} | 409
renew(lease_id)                 → {expires_at} | 410
release(lease_id)
read(key, if_none_match?)       → {bytes, etag}
write(key, bytes, if_match)     → {etag} | 412
commit(epoch, lease_id, batch)  → {applied} | 409
```

#### 失败语义

协调者不可达 → 全集群进入 §13.4 的降级：本地草稿、只读快照、对话不阻塞。

**MUST NOT** 在协调者不可达时"临时选一个客户端当仲裁者"——那正是脑裂的定义。

单机自用时，协调者退化为本地文件锁 + 本地 SQLite，不需要独立服务。**是否需要服务，取决于有没有第二个节点**，不取决于"要不要上云"。

## 15. 安全与权限

1. **解锁**：口令 → KDF → 解容器头 → 校验；参数与耗时约束见 `SECURITY_SPEC.md`。
2. **密钥生命周期**：仅在内存；退出清零；**MUST NOT** 写日志、崩溃转储、遥测。
3. **三层写权限**（v1.0.0 §4.4）：`state` 随时写；`traits` 仅睡眠、幅度受限、证据 ≥ 3；`kernel`（含 `permissions`）仅人工。**MUST** 在代码层拦截。
4. **能力权限与人格权限分离**：`permissions` 属内核，**MUST NOT** 随权重演化变化；模型无法自我提权。
5. **审计**：traits 写入、每次能力调用、seal、人格激活写哈希链；断号即拒绝启动。
6. **明文窗口**：运行期解密后的目录 **MUST** 仅本用户可读；`strict` 模式退出即删。**必须在文档里承认这个窗口**，不得宣称"全链路加密"。

---

> 本章其余条款（KDF、解锁、密钥生命周期）都**只在 `encryption_profile != none` 时适用**；选 `none` 不代表没有安全要求——它要求你在 `manifest.json` 里如实声明，并在文档与界面上说清楚「当前是明文」。

### 15.1 加密状态：可选，而且能来回转

加密不是一个"建库时按下去就定终身"的开关，而是**一份资产当前的状态**。三种档位写在 `manifest.json` 的 `encryption_profile` 里：

| profile | 密钥来自 | 典型场景 |
|---|---|---|
| `none` | 无 | 单机测试、物理隔离的机器、先跑通再加固 |
| `managed` | 口令（KDF 派生） | 日常使用、云端备份、多端漫游 |
| `device` | 口令 + 设备秘密 | 强绑定，通常伴随 `portable: false` |

**MUST**：`encryption_profile` 必须与实际字节一致。声明 `managed` 而盘上是明文，**MUST** 拒绝加载——这比不加密更危险，因为它让人以为已经安全了。

#### 转换命令

| 命令 | 转换 | 说明 |
|---|---|---|
| `seal` | `none` → `managed` / `device` | 读明文、加密、原子替换 |
| `unseal` | `managed` / `device` → `none` | **显式降级**，需要确认 |
| `rekey` | `managed` → `managed` | 只重包根密钥，载荷密文一字节不动 |
| `rebind` | `device` → `device` | 换设备；需旧设备或恢复短语 |
| `harden` / `loosen` | `managed` ↔ `device` | 加/减设备因子 |

#### 每次转换必须满足四条

1. **取独占写锁**（§13.2）。转换期间不接对话、不做结算——半个容器被读到的后果比停机严重。
2. **原子替换**：写临时对象 → 全量校验（逐文件哈希 + 记录数）→ `fsync` → rename。
3. **失败即回滚**：校验不过就保留原文件，**MUST NOT** 留下半个容器、**MUST NOT** 覆盖旧版本。
4. **写审计**：`(from, to, ts, actor)`；`unseal` 额外记 `downgraded_at`，让"曾经解密过"这件事永远查得到。

#### 降级不是罪，静默降级才是

数据是用户的，用户有权把密文解开。规范不禁止 `unseal`，只要求两件事：

- **MUST** 显式确认，并打印"此后明文可被同机任何进程读取"；
- **MUST NOT** 静默降级——没有提示、没有审计的解密，等于偷偷把保险箱门卸了。

**SHOULD**：`unseal` 只用于"导出给不支持容器的工具"这类临时需求，用完立刻 `seal`；如果打算长期用明文，应该正式切到 `none` 档并在 manifest 里声明，而不是"加密过又解开"留下一个含糊的状态。

**MUST**：读到不认识的 `encryption_profile` 一律拒绝加载，不得猜测、不得"先按明文试试"。

#### 开放格式承诺（反锁定）

一句判据：**如果只有我们的代码能解开它，那它就不是我们的格式，是新的牢笼。**

- **MUST**：容器字节格式、KDF 参数、AAD 规则、`manifest.json` 的全部字段，必须写在公开文档里（`docs/SECURITY_SPEC.md`）。
- **MUST**：任何第三方，不依赖本仓库的代码，仅凭文档即可实现读取、解密、迁移；不得依赖参考实现的内部行为（未写进文档的约定一律不算约定）。
- **MUST**：`none` 与 `managed` 两档必须能被纯文档实现；`device` 允许依赖设备秘密，但 **MUST** 同时写明如何用恢复短语在其他设备上解开。
- **MUST NOT**：给格式的**实现**设置许可费、专利主张或"需授权"条款。代码是 MIT；格式本身不设限。
- **MUST**：验收标准是**两个独立实现能互解**，而不是"我们的实现能读自己写的"。

最后一条是这条承诺唯一的硬证据。自己读自己不算验证——那只能证明编解码器自洽，证明不了格式可独立实现。

## 16. 档位与能力协商

| 档位 | 判定 | `num_ctx` | 模型 | 向量 | 加密 |
|---|---|---|---|---|---|
| **low** | < 6 GB | 4096 | 1.5B Q4 / 云端 | 关 | 建议 strict |
| **mid** | 6–20 GB | 8192 | 3B–7B Q4 | 可选 | 可选 |
| **high** | > 20 GB | 16384 | 7B–14B Q4 | 开 | 可选 |
| **thin** | 手机 / 浏览器 | 由 origin 决定 | 无（转发） | 无 | 不落盘 |
| **edge** | 机器人 / 嵌入式 | 由设备决定 | 本地小模型 + 云端 | 关 | 可选 |

**MUST** 由可用资源自动判定，可配置覆盖；阈值是档位的函数（v1.0.0 §6.6）。

`GET /syspersona/capabilities` **MUST** 同时返回模型能力与本机能力：

```json
{"spec": "1.2", "role": "gateway", "tier": "low",
 "model": {"stream": true, "tools": false, "ctx_max": 8192},
 "host": {"fs.read": true, "fs.write": true, "net.fetch": true,
          "proc.exec": false, "media.capture": false, "device.act": false},
 "personas": ["lin"], "degraded": []}
```

客户端 **MUST** 依此调整行为，**MUST NOT** 假设能力。

## 17. 合规：等级与 Profile

| 等级 | 名称 | 要求 |
|---|---|---|
| **L1** | 可对话 | 加载 / 组装 / 路由 / 归档，错误可见，逃生通道可用 |
| **L2** | 可连续 | + 记忆读写、睡眠、恢复指针、崩溃恢复、预算 |
| **L3** | 可迁移 | + 三种 DataSource、seal/unlock、binding、档位 |
| **L4** | 多设备 | + 在场模型（独占 / 并行）、租约与围栏、降级与回归、汇入溯源 |

| Profile | 形态 | 必过测试 |
|---|---|---|
| **E** | `embedded` | TC-C2/C3/C4、TC-M1–M3、TC-S1–S3、TC-A1–A3；TC-C1 用进程内适配器替代 |
| **G** | `gateway` | E 组 + TC-C1 + 全部 L/D/N 组 |
| **H** | `host-client` | G 组 + TC-N1–N21 |
| **R** | `edge`（具身） | G 组 + TC-A4/A5 + 反射延迟预算（§11.6） |

一个实现可同时声明多个 profile，分别给出证据。

```json
{"spec": "1.3", "profile": "G", "presence": "exclusive", "level": "L3",
 "impl": "python/3.12", "tests": {"TC-C1": "pass", "TC-A1": "pass"}}
```

**没有测试证据的声明不算合规**（与 v1.0.0 §17 同一标准）。

| | TC-N7 | 设备吊销 | 吊销后下一次请求 401，留审计 |
| | TC-N8 | DNS rebinding | 伪造 `Host` → 403 |
| **在场** | TC-N9 | 唯一在场（`exclusive`） | 两端同时对话 → 后到者 `409` |
| | TC-N10 | 交接连续性（`exclusive`） | B 首轮接上 A 最后一件事；epoch 递增；A 收 `displaced` |
| | TC-N11 | 过期接管（`exclusive`） | 心跳停 TTL 后接管 → 审计有记录，新会话从指针开始 |
| **结算** | TC-N12 | 结算独占 | 两节点同时 `/sleep` → 一个 202、一个 409 |
| **汇入** | TC-N13 | 汇入溯源 | 导入带 `source: graft`；traits 未变；画像偏移 ≤ 0.3 |
| **分支** | TC-N22 | 并行合并 | 两分支各 5 轮 → 合并后 episode 并集、无重复、带 branch 标记 |
| | TC-N23 | 分支认知 | 问"上午你在哪" → 区分本分支与另一分支，不声称在场 |
| | TC-N24 | 冲突标记 | 两分支学到相反事实 → 双方标 `contested`，不静默取新 |
| | TC-N25 | 并行经历不折扣 | 3 分支 1 天的权重演化仍守单次 ±2 / 7 天 ±5；证据计数 = 全部分支 episode 之和 |
| **租约** | TC-N18 | 围栏生效 | 旧 epoch 写入 → `409`，不产生任何行 |
| | TC-N19 | 心跳过期 | 停心跳 30 s → 另一节点接管，epoch+1，原持有者被拒 |
| | TC-N20 | 断连降级 | 拔网 → 一周期内 `degraded`；权威库无新写入；草稿有记录；对话不阻塞 |
| | TC-N21 | 回归不夺权 | 落后 epoch 重连 → `observer`，草稿 graft，即使本地时间更晚 |

## 19. 版本与扩展

- 规范版本走 `X-SP-Spec`；服务端回 `X-SP-Spec-Version`。
- 未知字段 **MUST** 忽略而非报错；未知错误码 **MUST** 按 `type` 归类处理。
- 新增能力 **MUST** 通过 `capabilities` 声明，**MUST NOT** 改变已有字段语义。
- 1.x 内保证：DataSource 接口、binding 结构、错误码语义、能力清单不变。

## 20. 局域网接入

- 默认 **MUST** 只监听 `127.0.0.1:8000`；对外是显式动作（`bind = "lan"`），**MUST NOT** 默认 `0.0.0.0`。
- 绑非回环后 **MUST** 强制鉴权；无 token 一律 `401`（唯一例外 `/healthz`，且不返回人格信息）。
- **MUST NOT** 暴露模型端口（Ollama 11434）——它没有鉴权。
- **MUST** 每设备一个 API Key（`spk_` + 32 字节随机），服务端只存哈希，**MUST NOT** 放 URL query，**MUST** 常量时间比较，吊销 5 s 内生效。
- **SHOULD** 用 HTTPS：iOS ATS 与 Android 9+ 默认禁止明文 HTTP。
- 反向代理 **MUST** 关闭响应缓冲，否则 SSE 会被攒住。
- **MUST** 默认关闭 CORS；需要网页客户端时用 origin 白名单，**MUST NOT** 用 `*`。
- **MUST** 校验 `Host` 头属于允许列表，防 DNS rebinding。

**新设备接入**：`device add` → 一次性配对码（5 分钟，限次）→ 客户端换长期 key（只显示一次）→ 之后只填 base URL。二维码内 **MUST NOT** 放长期 key。

## 附录 A：最小实现清单

一个 L2 级 Runtime 的最小构件：

1. 服务（HTTP 或进程内接口）+ 单 worker + 一把生成锁；
2. DataSource 的 `file://` 实现；
3. 三个 JSON 的加载与校验 + 一个 SQLite（FTS）；
4. 预算计算与尾部注入；
5. 模型转发（或直接调用）+ 流式转换；
6. 写队列 + 睡眠（指针、快照）；
7. 能力清单的三种裁决（allow / ask / deny）+ 动作记账；
8. 16 个错误码；
9. `X-SP-*` 头。

不需要：多用户、云端、租约、加密、向量检索、具身设备。

## 附录 B：常见错误做法

| 做法 | 为什么错 |
|---|---|
| 把记忆拼进开头 system | 摧毁前缀缓存，首 token 翻倍 |
| 每轮做一次抽取 | 低配设备直接卡死 |
| 每轮加密落盘 | KDF 1.6 s，聊天不可用 |
| 检索为空就静默继续 | 用户以为"它记得"，实际已失忆 |
| 多 worker 共享 SQLite | 写锁抖动，随机 `database is locked` |
| 自动合并两份 traits | 人格打架，且无法解释 |
| 手机存完整记忆库 | 丢设备 = 丢人格 |
| 把 `data/` 放进 OneDrive / SMB | SQLite 锁失效，静默损坏 |
| 默认模式下多设备同时对话 | 就是两个"它"，各自积累，无法合并 |
| 把 fork 当成"多端同步" | 新 UUID 已是另一个人 |
| 绑 `0.0.0.0` 且不开鉴权 | 全屋设备、访客 WiFi、恶意网页都能读记忆 |
| 暴露 Ollama 的 11434 | 模型端口无鉴权，等于开放本机 |
| 让模型自己拼 shell / 选路径 | 三个平台毁三次数；幻觉一次就够 |
| 把拒绝当成"模型没提需求" | 拒绝本身是信息，必须记账 |
| 用 200 掩盖降级 | 故障不可诊断 |

> 规范的完成标志不是被读完，而是**有人照着它做出了一个能通过 TCK 的实现，而你可以直接拿来用**。
