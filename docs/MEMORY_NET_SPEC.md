## 一、要解决的三件事

| 问题 | 现状 | 后果 |
|---|---|---|
| **分不清谁记的** | 会话都进同一个 `sessions\`，摘要里不标分身 | 同一件事多个模型各记一遍，看起来像三件 |
| **检索没有"来源感"** | 命中只给片段 | 不知道这条是电脑会话、手机、还是网页转述 |
| **改过就说不清** | 摘要覆盖式更新 | 事后问"当时为什么这么定"，答不上来 |

## 二、分身 ID（先定名，才谈统一）

格式：`<客户端>-<模型>`，例 `dsh-v4flash`、`hermes-v4flash`、`phone-web`。

- **不取专名、只留简称**（2026-11-09 定）——模型的出厂身份已经有了，别叠加；
- 每条归档、每条索引行、每条派发记录都带 `avatar`；
- 分身之间的差异**不合并**：同一条记忆两个分身都记，就是两条，靠 id 区分。

### 2.1 推导规则（v1.1 新增，照这张表写代码）

| 情况 | 规则 | 例 |
|---|---|---|
| 文件头有 `- 设备：` 与 `- 底座：` | `avatar = 设备 + "-" + 底座`（全小写、空白压成一个 `-`） | `笔记本-deepseek-v4flash` → `笔记本-deepseek-v4flash` |
| 只有 `- 底座：` | `avatar = "unknown-" + 底座` | `unknown-deepseek-v4flash` |
| 都没有 | `unknown`（**不猜**，见 §2.2） | `unknown` |
| 网页对话（历史兜底） | `网页-deepseek-web`（现行 `blocks()` 已有这条兜底） | `网页-deepseek-web` |
| 手机端 | 由抓取器写入 `- 设备：手机` | `手机-…` |

现状接线：`persona_search.blocks()` 已经解析出 `dev` / `mod` 两列（`blocks()` 返回 7 元组
`[rel, day, src, role, text, dev, mod]`），`--device` / `--model` 过滤也已能用。
本版要做的不是"再造一份"，而是**把 `dev`+`mod` 合成 `avatar` 这一个字段对外统一**。

### 2.2 历史文件：unknown 不猜（红线级的克制）

早期会话没有元信息头。可以按目录名推"网页 / 手机"（这是事实），**不许**按内容猜"这是哪个模型写的"。
`unknown` 就写 `unknown`——把猜测写成来源，比没有来源更坏，因为它看起来可信。

## 三、三层可溯源（从命中一路回到原文）

```
命中片段（带 source / avatar / 时间）
  → 分索引行：这一条属于哪个来源文件（`sessions\日期\来源\*.md`）
  → 原文：逐字可读
```

判据：**任意命中，3 步之内能读到原文的那一段**，且中间不经过"再总结一次"。

### 3.1 每层拿什么字段（v1.1 新增）

| 层 | 载体 | 字段 | 现状 |
|---|---|---|---|
| L1 命中 | 检索结果行 | `avatar` / `source` / `at` / `file` / `score` | 部分有（`dev`/`mod` 已解析，未合并成 `avatar`） |
| L2 分索引 | `index\L1.jsonl`（每文件一行） | `day` / `source` / `file` / `msgs` / `chars` / `head` / `mtime` | ✅ 已有 |
| L3 原文 | `archive\<日期>\<来源>\*.md` | 逐字 | ✅ 已有 |

`at` 取文件 `mtime`（isoformat），**只增不改**；同一会话被重新导出 → `mtime` 变了，视为新版本记录，旧行不删。

### 3.2 `--show-source` 的输出（v1.1 定死，便于机器读）

```
$ python persona_search.py "开工三步" --show-source --k 3
[1] 0.82  2026-11-09 18:41  dsh-deepseek-v4flash  archive/2026-11-09/电脑会话/x.md:87
    ── 原文 ──
    开工三步：读设定 → 读总索引 → 认领检查
    ...（前后各 2 行）
```

- 冒号后是**行号**；现在 `blocks()` 不记行号 → 落地时二选一：
  a) 检索时用片段在原文里 `find()` 现算（不改索引，慢一点但立刻可用）；
  b) `blocks()` 记账号（快，但要重建缓存）。
  **先 a 后 b**：a 能当天用，b 是优化，不是前提。

## 四、统一检索（一份索引，多种来源）

- **索引一份**（全局），备份各端独立（DECISIONS 十六：统一的是索引、不是备份）；
- 检索结果按 `avatar` 标注归属，同一句话被多个分身记过 → 合并显示但**保留全部来源**；
- 冲突不仲裁：两个分身的说法不同 → 两条都留，展示时按时间排，**不挑"更对的"**。

### 4.1 合并显示的规则（v1.1 新增）

同一段文本（归一后完全相同）被 ≥2 个 `avatar` 命中 → 显示一行，来源列写 `avatar-1, avatar-2`；
**文本不完全相同**（哪怕只差一个字）→ **不合并**，两条并排。
理由：合并的前提是"同一句话"，不是"同一个意思"——后者需要判断，而判断就是仲裁，§四 已经禁止。

## 五、记忆的可信度（不做分数，做时间）

不发明"重要度打分"——那会诱导人删记忆。只记三样：

| 字段 | 含义 |
|---|---|
| `avatar` | 谁记的 |
| `source` | 从哪来（会话 / 网页 / 手机 / 手动） |
| `at` | 什么时候记的（只增不改） |

"可信度"由人看时间与来源自己判断；系统不做裁判。

## 六、判据

1. **可溯源**：随便抽 10 条命中，10 条都能在 3 步内读到原文；
2. **不串味**：两台设备的同名会话不互相覆盖（按 `avatar` + 时间区分）；
3. **可重建**：删掉索引目录，能从 `sessions\` + `archive\` 重建，且命中集不缩水；
4. **不仲裁**：两个分身说法冲突时，检索仍能同时返回两条（不静默选一个）。

### 6.1 验收命令（v1.1 新增）

```
# ① 可溯源：抽 10 条，逐条打印 file:line，再核对那行确实在原文里
python persona_search.py "<关键词>" --k 10 --show-source
# 期望：10 行都带 file:line；抽查 3 条，原文该行含命中词

# ② 不串味：两台设备的同名会话共存
python persona_search.py "同名会话" --k 5 --device 笔记本
python persona_search.py "同名会话" --k 5 --device 手机
# 期望：两边都能返回，且 file 不同、avatar 不同

# ③ 可重建：索引目录改名 → 重建 → 命中集对比
ren index index.bak && python persona_index_l1.py
python persona_search.py "<同一关键词>" --k 100 > before.txt   # 与重建前结果比条数
# 期望：条数不缩水；缩水了就说明有索引是"只此一份"的

# ④ 不仲裁：构造两条来源不同、结论相反的记录，检索必须同时返回
python persona_search.py "<冲突关键词>" --k 10
# 期望：两条都在，avatar 不同，按 at 排序
```

## 七、边界

- 不合并分身（5.4 红线：分身合并要人点头）；
- 不为"整洁"删重复：重复是证据（同一件事被两个模型独立记下，本身说明它重要）；
- 不做跨设备实时同步——同步是文件层的事（FreeFileSync / 网盘），索引只负责"读得对"。
- **性格不进索引、检索不写性格**：性格面的规则只在 `AVATAR_SPEC` §8.1 定义，本规范只引用不重述——
  一句话：索引收录「知道什么」，`avatar` 的性格面属于「是谁」，两者不得互相写入。

## 八、容量与预算（v1.1 新增）

| 项 | 量级 | 说明 |
|---|---|---|
| 每块 `avatar` 开销 | 约 +20 B | 现在约 10 万块量级 → 总计 +2 MB 内存，可接受 |
| `--show-source` 的额外 I/O | 每命中 1 次读 1 个文件 | k=10 且去重后通常 <5 个文件，< 100 ms |
| 缓存失效 | 语料签名一变就重建 | 现有 `_CACHE_VER=4`；加字段要升到 5，**不升会读到旧缓存**（这是最容易出的错） |

## 九、落地拆解

1. `persona_index_l1.py` 的每行加 `avatar`（按 §2.1 从目录/文件头推断，缺省 `unknown`）；
2. `persona_search.py` 的结果带 `avatar / source / at` 三列（`avatar` 由 `dev`+`mod` 合成，不新读文件）；
3. `persona_master.py` 汇总时按 `avatar` 分组；
4. 溯源命令：`persona_search.py --show-source` 直接打印原文段落（先 `find()` 现算行号，见 §3.2）。

## 十、三个角色分开：保管 / 发票 / 汇总（v1.2 新增）

一台设备不必同时干三件事，**分开之后每件事都能单独换人**。

| 角色 | 干什么 | 凭什么 | 能不能换 |
|---|---|---|---|
| 会话保管 | 会话原文/索引放哪 | 目录本身 | 跟着库走 |
| **鉴定（发票）** | 给别的节点发限权票 | 钥匙文件 `%LOCALAPPDATA%\SysPersona\node-key.txt` | **能**：改 `issuer` 一行 |
| **汇总归档** | 合并索引、出归档 | 租约 `.aggregator-lease.json` | **能**：谁先起谁当，自动 |

三条硬规矩：

1. **钥匙只在本机文件里**，网盘上永远没有——网盘只放加密产物；
2. 票里写"谁签的"，验票时去 `ops/peers.json` 找那把钥匙，所以**发票方换了不用重签存量**；
3. 汇总权 ≠ 发票权。汇总谁当只看租约，发票谁当看配置。

### 10.1 汇总角色常驻（`SysPersona-SessionKeeper`）

租约 **90 秒过期**。靠"干活时顺手 claim"不可靠：夜里没人动，第二天谁先醒谁抢，
可能抢到一台正在忙的机器。所以改成**每分钟心跳**：

```
persona_session_keeper.py beat          # 持租约的续租；没持的只读不写
```

| 场景 | 行为 |
|---|---|
| `mode=disk`（会话库在本机） | **空转**：不写盘、不建租约、不吵 |
| `mode=cloud` 且无人持租约 | 拿下来 |
| `mode=cloud` 且自己持租约 | 续租（到期时间 +90 秒） |
| `mode=cloud` 且**别人持有效租约** | 不抢，只记 |
| `mode=cloud` 且别人租约**已过期** | 接手 |

状态写 `ops\keeper.json`（最新一份），状态**变化时**才往 `ops\keeper.jsonl` 追一行——
一分钟一条会把日志刷爆。

### 10.2 配对码（`invite` / `join`）

```
# 在 A 上：
persona_session_keeper.py invite     → SP1-eyJrIjog...
# 念给 / 抄到 B，在 B 上：
persona_session_keeper.py join SP1-eyJrIjog...
```

一串码 = `{"n": 节点名, "k": 钥匙}`。**别经网盘传**——念、抄、或用别的通道。
自己 join 自己的码会被拒（说明方向搞反了）；抄漏一个字符会报"读不出来"而不是静默登记错钥匙。

### 10.3 验收命令

```bash
python persona_session_keeper.py status   # 角色/心跳/钥匙指纹/对端登记 一屏
python persona_session_keeper.py beat     # 手跑一次心跳，看状态对不对
schtasks /query /tn SysPersona-SessionKeeper /v /fo list | findstr /i "状态 上次运行 结果"
```
