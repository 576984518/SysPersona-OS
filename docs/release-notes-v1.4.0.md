**范围**

规范说过「各记各的、合并是视角叠加」。这一版把它跑出来，同时把"合并"这个词定死：
**合并 = 记忆同步，不是并成一个库**。保存永远按来源保存。

`impl/launcher/avatar_poc.py`：零依赖，单机两个 SQLite 分支库模拟「电脑端 / 手机端」，
把两段平行经历同步进主库。要回答的是三个问题：

1. **同一件事被两个分身体验，同步时该去重还是留两条？** —— 留两条，**重复本身是证据**；
2. **要不要覆盖？** —— 不覆盖，任何一方都不改写对方已有的行；
3. **读的时候怎么区分？** —— 每条记忆都带来源（设备 / 分支 / 会话 / 模型），检索按来源呈现。

```bash
python impl/launcher/avatar_poc.py
```

**设计口径（2026-11-11 人定，写死）**

- **只是同步**：合并动作只做"收进来"，不做"合成一条"；不做跨来源去重，不做摘要替换；
- **按来源保存**：来源是记忆的一等字段，不是附注。同一件事两台设备各记一条，就是两条；
- **对账不覆盖**：同步前后两个来源库字节不变（不写回、不改写）；
- **检索客观**：检索只按内容与来源排序，不掺"哪条更像我"的主观权重。

> 这条口径同时决定了"分身合并"为什么后来不再是一个需要人点头的操作：
> 不同模型 / 版本的会话记忆本来就分开保存，所谓合并**就是读自己的记忆**。

```
PASS TC-AV1b  主脑可检索并区分来源                 [hits=4 branches=手机端分身/电脑端分身]
PASS TC-AV7   性格隔离：A 变 B 不变 / 检索不碰性格 / peer 不进漂移   [B未变=True 检索命中=0 漂移输入=1]

```

合并后的主库：**行数 = 两源之和，来源字段各不相同，没有一行被覆盖、没有一行被摘要替换。**

**边界**

- 本版只做"同机两分支"的同步；跨设备传输（NAS / 网盘 / 直连）在 v5.7 / v5.8 才成文；
- **不做冲突消解**：同一件事的两个版本都留着，判断交给人或检索时的排序；
- **不做加密**：当时的记忆是明文，加密在 v6.2 才进来；
- 派生件（索引、向量）不参与同步，重建即可。
