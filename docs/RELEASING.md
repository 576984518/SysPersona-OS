# 发布规则

> 一个版本号只回答一个问题：**"有没有交付新的、可验证的东西？"**
> 改几句话，不算。

---

## 一、什么才算一个版本

| 算 | 不算 |
|---|---|
| 新增可运行的产物（代码、容器、数据） | 措辞澄清、补例子、补链接 |
| 新增/删除条款，使旧实现掉出合规 | 把已有约束写得更清楚 |
| 改变默认语义或数据格式 | 排版、错别字 |
| 新增判据（TCK 条目） | 修订记录的补充 |

**判断方法**：如果这次改动不会让任何一个已通过测试的实现变得不合规，它就不配一个 Release。

---

## 二、规范只有一份现行页

- 规范文档（`docs/LAUNCHER_SPEC.md`）**就地修改**，不写"勘误 rN"、不在文末追加修正段。
- 版本页只有一个：**v1.1.0**，标题固定为「SysPersona Runtime 规范（现行）」，正文随修订更新。
- 所有变更记在 [`CHANGELOG.md`](../CHANGELOG.md) 与该页的「修订记录」表里：日期 / 改了什么 / 为什么。

理由：规范的读者只看最新版。把修正散在多个版本里，等于强迫他们做版本拼图。

---

## 三、版本号怎么给

| 位 | 什么时候升 | 例子 |
|---|---|---|
| **MAJOR** | 破坏性变更：数据格式不兼容、删除既有条款、改变身份语义 | 罕见 |
| **MINOR** | 新增能力、新增判据、新增交付物 | 加能力面、加实现 |
| **PATCH** | **基本不用**：修补与小的增补直接改进现有版本，不切新号 | 见 §十一 |

**文档修订不占号。** 它们只进 CHANGELOG。

---

## 四、Release 页必须有的四段

1. **范围**：这一版交付了什么，不包含什么。
2. **证据**：测试编号与结果、实测数字。没有证据的声明不算。
3. **边界**：明确"没做的部分"，防止读者以为已经能用。
4. **修订记录**：日期 / 改了什么 / 为什么。

**写法：写「设计与验证」，不写「补丁清单」。**（2026-11-09 定，他原话：「完全看不出我们设计了什么」。）

每页按这四问写，顺序固定：

1. **这一版只回答一个问题**——用一句设问开头（「唤醒之后到底发生了什么」「说不说得清是谁记的」）；
2. **设计**——机制、阈值、顺序；写死什么、不许做什么；能画就画一条线（ASCII 也行）；
3. **证据**——真跑的输出：编号 + 数字，贴原文，不写「已实现」；
4. **边界**——明确没做的部分，防读者以为已经能用。

**反例（不许再这样写）**：「新增 `x.py`、补了 §2.1、修了旧指针」——那是 `CHANGELOG` 的活。
版本页上这么写，读者只看得出"改过东西"，看不出**你设计了一个什么机制**。

**标题要自己会说话。**（2026-11-09 定，他原话：「现在你看名字，你知道这是什么吗？」）

- 格式：`vX.Y.Z — <领域>：<动作>`——看标题就知道这一版动了哪块、做了什么；
- 好例子：`检索：三条路可选`、`抓取：改按刷新触发`、`增量索引：假信号`、`记忆网络`、`后台处理`；
- 反例：`F5 触发`（只说了按哪个键）、`假信号`（不知道是谁的假信号）、`从设计到实现`（等于没说）。

**正文不要重复标题。** GitHub 已经把标题渲染成一级标题了，正文再从 `# v1.x.x — …` 开始，页面上就会出现两个一模一样的大字。正文直接从那句「本页会随勘误就地更新」的引用块开始。

页首固定一句：

> 本页会随勘误就地更新。规范全文以 `main` 为准。

---

## 五、撤销与合并

如果发现自己发了一个"只为一句话"的版本：

1. 删除该 Release 与对应 tag；
2. 内容并回现行页；
3. 在 CHANGELOG「撤销」一节记一笔，写明原因。

不要留着它"以保持历史完整"——**错误的版本比没有版本更贵**：它会被人读到、被引用、被照抄。

**同日的小步不必各自成版**：同一个功能的「缺口补丁」直接改进它的版本条目与 Release 正文，
删掉多切出来的 tag / Release，并在「撤销」一节记一笔（v5.3.1 / v5.3.2 → v5.3.0 即此例）。

---

## 六、标签与正文

- **tag 指向提交，是快照，原则上不动**（撤销的、以及同一版本内的修补并入时除外——
  此时 tag 随之前移，快照 = 该版本的最新状态）。
- **正文是活的**，随勘误就地更新。
- 两者冲突时，**永远以 `main` 为准**，并在页首写明这一点。

---

## 六点五、改完必须同步三处

**任何修改，都算未完成，直到下面三处一致：**

| 处 | 内容 |
|---|---|
| 规范正文 | `docs/LAUNCHER_SPEC.md`，条款本身 |
| 版本页 | v1.1.0 的正文摘要 + 底部「修订记录」 |
| 变更记录 | `CHANGELOG.md`，逐条原因 |

只改正文不改版本页，读版本页的人会照抄旧结论；只改 CHANGELOG 不改正文，等于只写了个公告。**三处不一致 = 没改完。**

这条之所以要单独写：文档不是代码，没有编译器提醒你"这里还有一处引用"。漏改不会报错，只会让下一个人读到一个自洽但过期的版本。

## 六点六、全局一致性检查（每次改完必做）

改一处规则，通常会在三到五处留下旧话。**不检查就提交，等于把矛盾留给读者。**

固定查这八条轴，逐条 grep：

| 轴 | 容易残留的旧说法 |
|---|---|
| 职责数 | 「四职责」（现在是五：加载 / 组装 / 路由 / 执行 / 归档） |
| 在场模型 | 「唯一在场」（现在是 `exclusive` / `concurrent` 两种） |
| 加密 | 「强制加密 / 默认加密」（现在是可选 `none` / `managed` / `device`） |
| 存储入口 | 「客户端直接读文件」（`managed` 下客户端不许碰存储） |
| 维护时机 | 「只在睡眠整理」（现在是睡眠 / 空闲 / 水位三种触发） |
| 版本引用 | 「规范 v1.2 / v1.3」（规范只有一个现行页） |
| TCK 编号 | 新增了 `TC-L4` / `TC-A*` / `TC-N2x`，合规表是否同步 |
| 数量断言 | 「12 / 15 个错误码」（现在是 16） |

做法：改完之后，把上表的词各 grep 一遍，逐条判断"这句还成立吗"。**发现即改，改完在 CHANGELOG 记一句"已做全局检查"及修正项**——不记，下一个人不知道这次扫过。

## 七、发布前自检

1. 这次改动会让某个已通过 TCK 的实现变得不合规吗？不会 → 不发版，只改正文 + CHANGELOG。
2. 现行页里的旧说法删干净了吗？（不是"后面补了一句"）
3. `CHANGELOG.md`、版本页、规范正文，三处是否一致？
4. 版本号是按第二节的规则给的，还是因为"觉得该发了"？
5. Release 页有没有"边界"一段？
6. 撤销过旧版本吗？撤了就写进 CHANGELOG。

---

## 八、历史包袱

本项目早期曾为文档修订连发 v1.3.0、v1.4.0，随后删除并合并。教训写在 `CHANGELOG.md` 的「撤销」一节——**留着一个错的版本，比没有版本更危险**。

## 九、版本对照表（2026-11-08 补）

本仓库同时存在四套版本号，它们**互不推导**，各自回答不同的问题。混用是误解之源，故立此表。

| 层 | 版本锚点 | 谁升 | 现例 |
|---|---|---|---|
| **仓库 / 发布** | git tag `vX.Y.Z` + Release | 发版（本文件 §一/§三） | `v4.1.0` |
| **运行时规范** | `docs/LAUNCHER_SPEC.md` 现行页内的版本号 | 条款变更（§二 就地改） | 规范 `v1.1` |
| **参考实现** | `impl/` 交付时的版本 | 代码交付 | 实现 `v1.2.0` |
| **人格文件** | `schema syspersona/persona@N` + `version` | 人格内容变更 | `@2` / `0.3.0-m1` |
| **工具** | 跟随仓库 tag | 随发版 | 同仓库 |

**规则**

1. 四套号**不互推**：仓库 `v4.1.0` 不代表规范 `v4`，也不代表人格版本；
2. 一次发版可以同时动多层，但 Release 正文必须写清**哪一层变了**（"范围"一段）；
3. 规范条款变更**不改仓库版本**（§二），除非同时交付了可运行产物；
4. 人格文件版本与仓库版本完全解耦：人格 `0.3.0-m1` 可以跑在仓库 `v4.1.0` 上，反之亦然；
5. 引用版本号时必须带层名，例：「规范 v1.1」「实现 v1.2.0」「人格 0.3.0-m1」，不写裸号。

## 十、发版节奏（2026-11-09 定；同日改为一功能一版本）

本项目定位是**参考实现与架构白皮书**，不追求"一版解决全部问题"。因此：

1. **一个功能 = 一个版本**；功能内的增补与修补**直接改进这个版本**，不切新号；
2. 不必等"功能完整"，也**不允许**为改几句话发版（§一 不变）；
3. **唯一硬约束**：不得重复、不得前后矛盾；**改了新的，旧的必须同步对应**——改一处要扫全库；
4. 版本号按 §三，但 **PATCH 基本不用**：修补并入现有版本（§十一）；只有破坏性变更才升 MAJOR。

## 十一、一功能一版本（2026-11-09 定）

> 一句话：**版本是功能的抽屉，不是提交的计数器。**

1. **新增功能** → 一个 MINOR；版本号只在这一刀切下去时出现。
2. **同一功能发布后仍在补**（缺口、边界、措辞、实现细节）→ 直接改该版本的条目、Release 正文与代码，
   **不新开 PATCH**；改完 tag 随之前移，Release 页就地更新。
3. **破坏性变更**（数据格式不兼容、删条款、改身份语义）→ 才升 MAJOR，且单独成版。
4. **什么时候必须记 CHANGELOG**：任何改动都记；但记的是「这一版改了什么」，不是「又发了一版」。
5. **什么时候删版本**：同一天为同一功能切出的多个号，合并回一个，删 tag / Release，
   在「撤销」一节留痕——留一个错版本比没有版本更贵。

反例（本规则就是被它逼出来的）：2026-11-09 一天之内为「重试上限」「保活只报不拉」各切一版
（v5.3.1 / v5.3.2），四十分钟后又全部并回 v5.3.0。**第一次就该并进去。**
