## 一、为什么不能各记各的

多端（电脑、手机、网页、别的模型）都能总结出待办。如果各自留一份：
两个人就会做同一件事，或者都以为对方在做——**这不是效率问题，是相互抹杀**。

所以：**生成归各端，登记与分发归服务端。**

## 二、一条任务的旅程

```
任一端总结 → 产出「待办候选」
   → 上交服务端（不是本地文件）
   → 服务端小模型：去重 + 合并 + 排优先级 + 按人/能力匹配
   → 进入任务池（pending）
   → 派发给「最近报到过」的分身（v5.3 两道门）
   → 分身 ack（接手）→ 执行 → done（带证据）
   → 超时未接手：标 expired → 改派（最多 3 次）→ failed + 告警
   → **一圈都被拒 / 都不在线：进等待区（queued），不丢弃**
        → 每 5 分钟扫一次节点池，有 idle 就派
        → 排队超 24 小时：failed + 告警（§四）
```

## 三、服务端要做的三件事（其余都不做）

| 事 | 规则 |
|---|---|
| **合并** | 同一件事的多种说法 → 一条；保留全部来源 id（可回溯） |
| **排序** | 一级 1–10 按顺序；同优先级内按依赖/时间；**不做"我觉得更重要"** |
| **匹配** | 按人的指令 > 能力标签 > 最近报到时间；能力不足的不派 |

服务端的小模型**只做结构化整理**，不做价值判断，不写记忆正文。

### 3.1 合并规则（先规则，后模型）

规则版三条，够用就不上模型：

1. **同标题归一**：去掉标点/空白、全角转半角、小写后完全相等 → 合并；
2. **词袋重叠**：中文按 2-gram 切，Jaccard ≥ **0.6** → 判为同一件事（阈值写死，方便复核）；
3. **否决优先**：任一来源标了 `reject: true` → 该条**不合并、直接落 `rejected`**（人说"不要"最高优先）。

合并结果必须带 `source_ids: [...]`——**全部**来源 id，一个都不许丢；丢了就不可回溯（判据 4）。

### 3.2 排序规则

- `prio` 取 **1–10**（1 最先），由生成端给，服务端**只校正不发明**：范围外的夹到 1 或 10，缺省 5；
- 同 `prio` 内：先按 `deps` 拓扑（依赖未完成的不排前），再按 `created_at` 先到先做；
- **禁止**"服务端觉得重要就提前"——那项判断属于人，服务端最多标 `hint` 字段，不改序。

## 四、重派与排队：服务端绝不干等（v5.5 核心）

> 一句话：**节点有拒绝权，服务端就没有"再问一遍"的权利，只有"换一个"和"先记着"。**
> 任务不会因为没人接就消失，它只会变得更旧——而变旧要能被看见（24 小时熔断）。

### 4.1 五种状态，两个池子

| 对象 | 状态 | 含义 |
|---|---|---|
| **任务** | `pending` | 已在任务池，还没派 |
| | `queued` | **派过一圈，全被拒/全离线 → 进「待派发等待区」**，等节点变 idle 再来 |
| | `accepted` / `running` | 有人接了，正在干 |
| | `done` / `failed` | 结束；`failed` 只在熔断时出现 |
| **节点** | `idle` | 空闲，能接 |
| | `busy` | 手上有活，或被拒后**立刻标 busy**（防这一轮又选到它） |
| | `offline` | 没报到 / 超窗口 |

**"被拒就标 busy"是这套逻辑里最容易漏的一步**：不标的话，下一轮遍历又会选中同一个节点，
形成"问一遍→被拒→再问它"的死循环，看着在派，实际一步没走。

### 4.2 派发主循环（伪代码，落地照抄）

```python
def dispatch(task, nodes):
    """服务端派一条任务。返回 'accepted' | 'queued'。"""
    for node in nodes_online(nodes):              # ① 只遍历在线节点
        if node.state != "idle":                  # ② 只要空闲的
            continue
        r = ask(node, task)                       # ③ 下发（带 task_id + 超时）
        if r == "accept":
            task.state = "accepted"
            node.state = "busy"                   #    接了 → 节点忙
            return "accepted"
        if r == "reject":                         # ④ 被拒：节点有更高优先级的活
            node.state = "busy"                   #    ★ 立刻标忙，这一轮别再选它
            continue                              #    换下一个，不重试同一个
        if r == "timeout" or r == "offline":
            node.state = "offline"                #    叫不应就当它不在
            continue

    task.state = "queued"                         # ⑤ 一圈走完没人接 → 进等待区
    task.queued_at = now()
    return "queued"                               #    ★ 绝不丢弃


def tick():                                       # 每 5 分钟一次
    for task in queued_tasks(sort="queued_at"):    # 先排队的先派
        dispatch(task, nodes)
    for task in queued_tasks():
        if now() - task.queued_at > 24 * 3600:    # ⑥ 24 小时熔断
            task.state = "failed"
            alert("error", "task-expired", task, "排队超过 24 小时无人可派")
            remove_from_queue(task)
```

**为什么先排队的先派**：等待区不是栈。后到的先派，会让最老的任务永远排在最后——
而"最老的"恰恰是最可能已经过期的。

**`queued_at` 只在第一次入队时打**（写参考实现时才发现的坑）：如果每轮重派都把它刷成"刚刚"，
24 小时熔断**永远不会触发**——池子天天被拒，任务永远"刚排上"。同理，`tick()` 里**先熔断、再派发**，
顺序反了等于给过期任务多一次派发机会。

### 4.3 与 v5.3 本地派发的关系（别写成两套）

| 环节 | v5.3（本机已有） | v5.5（服务端新增） |
|---|---|---|
| 换人上限 | 超时改派最多 3 次 | **不变**——但**"被拒"不计入这 3 次**：拒绝是节点主动打回，不是无人认领 |
| 超时 | ttl 600 秒未 ack → expired | 不变；服务端多一层 24 小时排队熔断 |
| 门禁 | 报到门 + 两道索引门 | 不变（节点侧的规矩，服务端不改） |
| 报错 | 写 `ops/alerts.jsonl` | 同一条通道，字段一致 |

**同一套代码**（§四）：`dispatch()` 与 `tick()` 跑在服务器上是服务端，跑在本机就是本地派发器。
本机不开 `tick()`——**本机不排期**，排期是服务端的事（见「附：云端服务唤醒」）。

### 4.4 判据（四条，少一条都算没做）

1. **正常派发**：有 idle 节点 → 一条任务只问一次就 `accepted`；
2. **被拒换人**：第一个节点回 `reject` → 该节点变 `busy`，任务在同一次调用里落到第二个节点；
3. **全拒排队**：所有在线节点都拒 → 任务变 `queued` 且**没丢**（能在等待区查到，带 `queued_at`）；
4. **熔断**：把 `queued_at` 拨到 25 小时前 → 下一次 `tick()` 标 `failed` 并写告警。

> 四条都可以用假节点跑，不需要真服务器——参考实现 `tools/persona/persona_sched.py --selftest`。

## 五、同一套代码

服务端与本地守护**是同一个程序**（`persona_*`）：跑在服务器上是服务端，跑在本机是中间件。
理由：两边逻辑（认领、派发、超时、告警）本来就一样，分两套写必然走偏；
本机可以完全离线跑（单人单机 = 自给自足），有服务端就自动切到"共享池"。

### 4.1 数据契约（v1.1 新增）

一条任务（JSON，`POST /tasks` 的体与 `outbox.jsonl` 的行同构）：

```json
{
  "id": "t-20261109-a1b2c3",
  "title": "给 persona_gauge 加 --ctx 测试档",
  "prio": 3,
  "deps": ["t-20261109-9z8y7x"],
  "cap": ["python", "text"],
  "source_ids": ["s-20261109-1905-07"],
  "source": "summary",
  "created_by": "dsh-deepseek-v4flash",
  "created_at": "2026-11-09 19:40:02",
  "reject": false,
  "status": "pending",
  "assignee": "",
  "note": ""
}
```

- `id` = `t-<YYYYMMDD>-<6 位随机>`；**幂等键就是 `id`**：同一个 id 重复上交，服务端返回 200 + 已有记录，不新建；
- `status ∈ {pending, claimed, running, done, expired, failed, rejected}`；
- 状态变化**追加**到 `ops/tasks.jsonl`，同 id 以最后一行为准（与 `dispatch.jsonl` 同构，不原地改）。

### 4.2 HTTP 契约（最小三接口）

| 方法 | 路径 | 作用 | 语义 |
|---|---|---|---|
| `POST` | `/tasks` | 上交 | 幂等（按 `id`）；成功 201，已存在 200 |
| `GET` | `/tasks?agent=<id>` | 拉取可认领 | 只返回 `pending` 且 `cap` 匹配 `agent` 的；按 §3.2 排好序 |
| `POST` | `/tasks/<id>/ack` | 接手 | 成功 200；已被别人认领 → **409**；能力不足 → **403** |

- 只绑 `127.0.0.1`（跨机由文件同步/隧道解决，服务端不开公网）；
- 无服务端时，同一套代码走本地 JSONL，**接口语义不变**（调用方不需要分支）；
- 认证：本机回环免鉴权；非回环必须带 `X-Persona-Token`（一次性密钥，用完即删，不进文件）。

## 六、判据

1. **不重复**：两个分身同时看到同一条任务，只有一个能 `claim` 成功（另一个拿到 exit 1）；
2. **不丢**：服务端不可用时，本机队列继续跑，恢复后补交（本地留 outbox，不丢单）；
3. **不卡**：超过 3 次改派一律 `failed` + 告警，不允许"看起来在处理"；
4. **可回溯**：任一任务能查到「谁在什么时候把它从哪条总结里提出来的」。

### 5.1 验收命令（v1.1 新增）

```
# ① 不重复：两个进程同时抢同一条
start /b python persona_claim.py claim t-1 "并发测试" --by agent-a
start /b python persona_claim.py claim t-1 "并发测试" --by agent-b
# 期望：一个 exit 0，另一个 exit 1；ops/task-claims.jsonl 只有一条 claim

# ② 不丢：停服务端 → 交 1 条 → 起服务端 → 看补交（persona_tasks.py 是本版要新增的）
python persona_tasks.py submit --title "离线补交测试"      # 期望：outbox.jsonl +1，status=pending
python persona_tasks.py serve --once                      # 期望：outbox 清空，tasks.jsonl +1

# ③ 不卡：把 TTL 调成 1 秒，连跑 reap（reap 在 persona_report，不在 dispatch——dispatch 是模块，没有 CLI）
python persona_report.py reap --ttl 1 --max-retry 3
# 期望：第 4 次时 status=failed，ops/alerts.jsonl 有 error 行

# ④ 可回溯：任取一条 id，能链回总结
python persona_tasks.py show t-20261109-a1b2c3             # 期望：打印 source_ids 与对应总结文件
```

## 七、边界

- 托盘只显示，不决策；决策在服务端（没有服务端时在主节点）；
- 任务池不是记忆：任务记录进 `ops/`，**不进 `memory/`**，不参与画像；
- 不做"自动派活给不认识的节点"：只派给最近报到过、能力匹配的；
- 不合并"人明确说不要"的条目（否决票最高优先）。

| 文件 | 增长 | 策略 |

## 附：云端服务唤醒（与 v5.3 唤醒的接口）

> 「醒 → 报 → 领」这条链的完整规则与三道门见 [`INTERACT_SPEC.md`](INTERACT_SPEC.md) §三；
> 本节只讲**第三类唤醒**（云端服务）怎么接进那条链。

唤醒分三类，界线是**谁决定什么时候醒**（2026-11-10 定）：

| 类别 | 谁决定 | 落在哪 |
|---|---|---|
| 心跳唤醒 | 守护进程 | `persona_daemon` 的 `wake` 任务，30 秒一扫，只维护不打扰 |
| 自主定时唤醒 | **分身自己** | `persona_wake.py add --in N --purpose ...`；每完成一个任务就给自己排下一次 |
| **云端服务唤醒** | **服务端调度** | 本节：由任务调度决定谁该醒、醒了领哪件活 |

**事件唤醒不另立一类**（B74，2026-11-10 落地）：决定什么时候醒的仍然是**守护进程**，
只是触发条件从"到点"扩成"有事"——派发一条活出去，立刻给收件人排一个 N 秒后的闹钟，
不必等它下一次自己想起来。

```
派发一条活 → persona_wake.event(agent, "新活：…", delay=5)
            → 同一个分身已有未到点的闹钟就**合并**（不堆一串）
            → 守护 30 秒内扫到 → 摘简讯 + 自动报到（read_index=是）
            → ops/wake-events.jsonl 记「谁在什么时候被什么事件叫醒」
```

界线仍然只有"谁决定"这一条：**到了点（人/分身排的）→ 自主定时；有事了（系统扫到的）→ 心跳的事件触发；
服务端说有活 → 云端。** 三类，不多不少。

云端服务唤醒的三步（本机只做后两步，不自己排期）：

```
服务端：有活 → 选一个够格又醒着的分身 → 发「唤醒指令」（带 task_id + purpose）
本机  ：收到指令 → persona_wake 登记一条即时闹钟（--in 0）→ 到点摘简讯、执行 purpose
分身  ：报到（read_index=true）→ 走两道门认领 → 领到就干，领不到就回「我不够格」
```

**为什么本机不排期**：排期要全局视野（谁在线、谁忙、谁擅长），单机看不到；
本机硬排只会和别的节点抢同一件活。所以本机只负责「被叫醒 → 报到 → 领活」。

**与 v5.3 的关系**：v5.3 已经做好的「闹钟 → 简讯 → 报到 → 两道门派发 → 超时改派」正好是这条链路的下半截；
v5.5 补的是上半截（服务端决策 + 全局视角）。
