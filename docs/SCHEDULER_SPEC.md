# 任务调度（SCHEDULER SPEC）— v5.5

> 状态：**设计成文，未落地**。v5.3 已交付其中"派发 + 超时回收"那一半。
> 一句话：**活儿先交服务端，再从服务端认领；本地不留私有任务池。**

## 一、为什么不能各记各的

多端（电脑、手机、网页、别的模型）都能总结出待办。如果各自留一份：
两个人就会做同一件事，或者都以为对方在做——**这不是效率问题，是相互抹杀**。

所以：**生成归各端，登记与分发归服务端**。

## 二、一条任务的旅程

```
任一端总结 → 产出「待办候选」
   → 上交服务端（不是本地文件）
   → 服务端小模型：去重 + 合并 + 排优先级 + 按人/能力匹配
   → 进入任务池（pending）
   → 派发给「最近报到过」的分身（v5.3 两道门）
   → 分身 ack（接手）→ 执行 → done（带证据）
   → 超时未接手：标 expired → 改派（最多 3 次）→ failed + 告警
```

## 三、服务端要做的三件事（其余都不做）

| 事 | 规则 |
|---|---|
| **合并** | 同一件事的多种说法 → 一条；保留全部来源 id（可回溯） |
| **排序** | 一级 1–10 按顺序；同优先级内按依赖/时间；**不做"我觉得更重要"** |
| **匹配** | 按人的指令 > 能力标签 > 最近报到时间；能力不足的不派 |

服务端的小模型**只做结构化整理**，不做价值判断，不写记忆正文。

## 四、同一套代码

服务端与本地守护**是同一个程序**（`persona_*`）：跑在服务器上是服务端，跑在本机是中间件。
理由：两边逻辑（认领、派发、超时、告警）本来就一样，分两套写必然走偏；
本机可以完全离线跑（单人单机 = 自给自足），有服务端就自动切到"共享池"。

## 五、判据

1. **不重复**：两个分身同时看到同一条任务，只有一个能 `claim` 成功（另一个拿到 exit 1）；
2. **不丢**：服务端不可用时，本机队列继续跑，恢复后补交（本地留 outbox，不丢单）；
3. **不卡**：超过 3 次改派一律 `failed` + 告警，不允许"看起来在处理"；
4. **可回溯**：任一任务能查到「谁在什么时候把它从哪条总结里提出来的」。

## 六、边界

- 托盘只显示，不决策；决策在服务端（没有服务端时在主节点）；
- 任务池不是记忆：任务记录进 `ops/`，**不进 `memory/`**，不参与画像；
- 不做"自动派活给不认识的节点"：只派给最近报到过、能力匹配的；
- 不合并"人明确说不要"的条目（否决票最高优先）。

## 七、落地拆解

1. `persona_claim` 已在本地跑通 → 补 `outbox`（离线时暂存待上交）；
2. 服务端 API：`POST /tasks`（上交）、`GET /tasks?agent=`（拉取）、`POST /tasks/{id}/ack`；
3. 合并器：先用规则（同标题归一 + 关键词重叠）跑通，再谈小模型；
4. 托盘加"任务池"只读视图。
