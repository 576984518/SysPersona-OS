# 文档修订策略

> 一句话：**就地改，别打补丁；改了要记账；读者只信 `main`。**

---

## 一、为什么不写"勘误 rN"

打补丁的典型形态是：正文不动，文末写一段"修正：上文第三条应为……"。

它有三个问题：

1. **没人读到底。** 正文里的错误条款仍然在，复制粘贴的人拿走的还是错的。
2. **越打越长。** 三轮之后，读者要在正文与勘误之间来回对照，成本高过重读。
3. **版本含义变得模糊。** "v1.1 到底是什么意思"取决于你哪天读的。

所以本仓库采用相反的做法：**发现错误，直接替换原句**。理由与日期记进 `CHANGELOG.md` 与该版本的「修订记录」。

---

## 二、什么算"条款级变更"，必须记账

| 类型 | 例子 | 记账 |
|---|---|---|
| 新增 / 删除 **MUST** | 新增"能力调用必须记账" | 必须 |
| 改判据 | TC-N25 从"≤ 1.2 倍"改为"守 ±2 / ±5" | 必须 |
| 改默认值 | 默认 `num_ctx` 从 4096 改 8192 | 必须 |
| 改接口 / 错误码 / 字段 | 新增 `policy_denied` | 必须 |
| 纠正错误陈述 | 把"较晚活动者"改成"先取得租约者" | 必须 |
| 措辞、排版、错别字 | 把"它门"改成"它们" | 不必 |

**门槛很低**：只要它能让一个已通过 TCK 的实现变得不合规，就必须记账。

---

## 三、版本号什么时候升

- **不升**：措辞澄清、补例子、补链接、把已有约束写得更清楚。
- **升小版本**：新增章节、新增判据、明确一条此前含糊的边界。
- **升大版本**：数据格式破坏性变更、删除既有条款、改变默认语义。

按这个标准，v1.1.0 里的"形态无关性"与"租约"属于**补清楚已有约束**，当时也可以不升版；实际升了，是因为它们把 `L1` 的适用范围收窄了——收窄会让旧实现掉出合规，算条款级变更。

---

## 四、版本页的写法

每个 Release 页底部必须有「修订记录」：

| 日期 | 改了什么 | 为什么 |
|---|---|---|

并且页首要有这一句：

> 本页会随勘误就地更新。规范全文以 `main` 为准；本页只描述该版本交付了什么。

**标签（tag）不动。** tag 指向提交，是"当时的快照"；文档在 `main` 上继续被修正。两者冲突时，**永远以 `main` 为准**。

---

## 五、什么时候不要"就地改"

只有一种情况：**已经有人依赖这个版本的行为**（有外部实现、有 fork、有引用）。

那时正确做法是：旧版本冻结并标注 `superseded`，新版本承接修正，并在两者页首都写清"哪份是现行"。本仓库目前没有外部依赖者，所以采用就地修改；一旦出现外部实现，这条要改。

---

## 六、自检

改完问三个问题：

1. 我把错的那句删掉了吗？（不是"在后面补了一句"）
2. `CHANGELOG.md` 与版本页的「修订记录」里，有这次的日期与原因吗？
3. 有没有第二处引用了旧说法？（`grep` 一遍关键词再提交）

第三条最容易漏：规范里同一个规则往往在三处出现——正文、TCK、版本页。改一处等于没改。

## 七、不发文档版本

文档修订**不建 Release**。Release 只在交付可运行产物（代码、容器、数据）时创建。

规范页只有一个现行版本（v1.1.0），正文就地改；变更记在 `CHANGELOG.md` 与该页的「修订记录」。

详细规则见 [`RELEASING.md`](RELEASING.md)。这条是吃过亏之后加的：曾为文档修订连发 v1.3.0、v1.4.0，读者被迫在版本间拼图——那正是本项目要解决的问题。
