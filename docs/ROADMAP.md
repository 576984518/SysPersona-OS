### 唤醒的三种来源

| 来源 | 谁发起 | 语义 |
|---|---|---|
| 定时唤醒 | 人（托盘里配周期/时刻） | 像闹钟：到点就醒 |
| 任务唤醒 | 智能体自己 | 「我需要在 X 时候醒来做 Y」——登记给常驻程序 |
| 事件唤醒 | 系统（任务池/依赖） | 有新任务或依赖完成时叫醒相关分身 |

**闹钟语义**：登记时必须带两样——**什么时候**（时刻或周期）和**醒来做什么**（purpose）。
到点后：摘简讯 → 执行 purpose → 结果回传 → 关闭或按周期继续。
没有 purpose 的闹钟一律拒绝登记（防「醒了不知道干什么」的空转）。

登记落盘 `ops/wake.json`；常驻程序每 30 秒扫一次，触发后写 `ops/wake-fires.jsonl`。

### 自调度：做完事自己定下一个闹钟

不是「睡着等下一次唤醒」的循环，而是**任务驱动的自调度**：

```
闹钟响 → 读总索引 → 认领任务 → 执行
      → 完成后判断：还有后续要等（编译/下载/等人回）或暂时没事
      → 自己再登记一个闹钟（1 分钟后 / 5 分钟后 / 预计完成时）
      → 本轮结束；到点再被拉起
```

**为什么必须有这一步**：智能体不会自己醒来。没有「完成后自设下一闹钟」，
任务一旦做完就永久停摆——没人叫它，它就再也不会动了。

登记同样受 purpose 约束：下一个闹钟也要写清「醒来做什么」。

### 派发超时回收（v5.3 补）

`pending` 超过 ttl（默认 600 秒）没人接手：追加一条 `expired`，再追加一条**改派**的新 `pending`；
原记录不覆盖。有醒着的分身才改派，没有就只记「无人可改派」——
不加这一条，一次掉线会让任务永久挂在「派发中」，而总索引里看起来一切正常。

**换人上限（v5.3.1 补）**：`retry_count` 到 3 仍无人接手就标 `failed` 并写 `ops/alerts.jsonl`。
没有上限的改派是另一种死循环：任务在分身之间一直转手，看起来永远「处理中」，实际永远做不成。

### 边界

- 代理不做跨设备、不做公网、不当远程 shell；
- 进程查询在受限令牌下可能被过滤，因此返回值是三态：查不了就不动手。


## v5.4.0 — 后台处理（**已交付**）

**目标**：上下文快满时，程序自己量、自己压，人不用盯着数。

- 梯子（按真实到得了的线重排）：150K 注意 / 250K 备包 / 300K 镜像+出包 / **350K 敲压** / 1M 断；
- 闭环：每 5 分钟量一次 → 到线 → 冷却 900 秒未过就跳过 → **先镜像落盘（sha256 自证，落不了就不压）** → 不打断人 → 敲 `/compact` → 壳自己压 → 水位回落；
- 借壳不造轮：压缩是壳的活（它手里才有完整历史），我们只负责**量得准、敲得准**；
- 闹钟挂在**系统计划任务**上，不挂在会话里——会话一被压缩换掉，会话级闹钟就跟着没了（实测）。

规格 `docs/BACKGROUND_SPEC.md`（v1.5），实现 `persona_compact.py`（走 `persona_inject.py` 的注入通道）。
**还欠**：摘要实体校验（防压没了）未做；托盘还没有「立即压缩」手动项。
