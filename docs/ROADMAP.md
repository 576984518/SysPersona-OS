## v5.3.0 — 保活 + 交互代理（待做）

**保活**：监控智能体进程，卡死或未运行就拉起；记录拉起原因与次数。

**交互代理**：智能体里的 AI 通过本程序调用本机系统（脚本、文件、进程）。

**定时唤醒的完整动作链**（关键，不只是"拉起来"）：

```
唤醒 → 重读总索引（所有来源汇总） → 知道后面发生了什么
     → 再连后台服务 → 看有什么能做 → 认领任务
```

**索引分两层**：
- **总索引**：所有来源（各客户端、各分身、各设备）汇成一份，回答"全局发生过什么"；
- **分索引**：每个来源各有一份，回答"这条具体来自哪"。
唤醒后**先读总索引**，再决定做什么；不读索引就认领 = 盲干。


### 唤醒的三种来源（v5.3 细化）

| 来源 | 谁发起 | 语义 |
|---|---|---|
| 定时唤醒 | 人（托盘里配周期/时刻） | 像闹钟：到点就醒 |
| 任务唤醒 | 智能体自己 | 「我需要在 X 时候醒来做 Y」——登记给常驻程序 |
| 事件唤醒 | 系统（任务池/依赖） | 有新任务或依赖完成时叫醒相关分身 |

**闹钟语义**：登记时必须带两样——**什么时候**（时刻或周期）和**醒来做什么**（purpose）。
到点后：唤醒 → 读总索引 → 执行 purpose → 结果回传 → 关闭或按周期继续。
没有 purpose 的闹钟一律拒绝登记（防止「醒了不知道干什么」的空转）。

登记落盘 `ops/wake.json`；常驻程序每 30 秒扫一次，触发后写一条唤醒记录（来源、purpose、结果）。


### 自调度：做完事自己定下一个闹钟（v5.3 关键）

不是「睡着等下一次唤醒」的循环，而是**任务驱动的自调度**：

```
闹钟响 → 读总索引 → 认领任务 → 执行
      → 完成后判断：还有后续要等（编译/下载/等人回）或暂时没事
      → 自己再登记一个闹钟（1 分钟后 / 5 分钟后 / 预计完成时）
      → 本轮结束；到点再被拉起
```

**为什么必须有这一步**：智能体不会自己醒来。没有「完成后自设下一闹钟」，
任务一旦做完就永久停摆——没人叫它，它就再也不会动了。

登记同样受 purpose 约束：下一个闹钟也要写清「醒来做什么」。
