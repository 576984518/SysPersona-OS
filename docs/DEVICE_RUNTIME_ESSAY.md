# 一台接了记忆的机体该怎么运转

> **SysPersona-OS** · 本文件定义：运行设计的成文版（给人读的那一篇）
> 规范全文以仓库 `main` 为准；改了要同步 README / CHANGELOG / 台账。

SysPersona-OS 的协同工作流可以概括为：**每台设备都是本地采集与落盘的宿主，云端模型只负责推理；记忆本体只有一份、按来源保存，通过增量同步与身体租约在设备之间协同；任务靠带锁认领避免重复执行；断网时本地容灾，恢复后继续追赶。**

它和市面上"本地大模型机器人"的根本区别在于：那些方案把算力全放在本地，解决的是一台机器"没网也能动"；这一套把记忆、规则、人格抽出来，做成可以跨设备、跨模型流转的底座，解决的是"换台机器还是同一个、断网不失忆、回来能追上"。

## 与本地大模型机器人的根本区别

1. **运行逻辑的本质不同**
   本地大模型机器人是一颗"单机大脑"，核心是感知、思考、执行闭在一个盒子里，算力主要用来处理眼前的视觉、听觉和动作。SysPersona-OS 更像一套"分布式灵魂中枢"：它不要求设备本地有多强的推理能力，而是把记忆、规则、人格抽出来，变成一个跨设备、跨模型流转的底层系统。

2. **云端主导，本地兜底**
   日常主力是云端大模型，为的是拿到最强的推理能力：**所有需要思考的环节——理解、规划、判断、写作、改记忆——都在云端完成**。这里的"云端"指的是**服务端角色**，不是某家公网厂商：可以是 DeepSeek、千问这类公网 API，也可以是自己搭的一台推理服务器——局域网里的 GPU 机、家里的服务器、甚至本机另起的服务进程，只要它承担推理与仲裁，它就是"云端"。判据是它在系统里干什么，不是它在不在公网。本地不当大脑，当底座——记忆落盘、索引、压缩、任务池、自检、断网兜底都在本地。本地模型也不是第二个大脑：它只做**采样输出**（取几个候选、粗筛、草稿片段）和断网时的容灾，不参与决策。所以它高度依赖网络，但断网时不会立刻失忆：记忆和规则做成文件，仍能检索、仍能维持人格，只是推理和协同变弱。

3. **多设备协同与记忆共享**
   纯本地机器人的记忆是孤岛，换个设备记忆就断了。这一套的核心价值恰好在这里：记忆不是每台各存一份，而是只有一份本体、按来源保存，设备之间做增量同步，任务池带锁认领。设备只是执行端，真正的"智能体"在云端算力和本地记忆层之间穿梭。

## 协同工作流

1. **事件采集**
   每台设备持续抓取窗口、文件、操作事件，按刷新事件触发归档。采集在本地发生，因为只有本地知道"刚才屏幕上发生了什么"。

2. **本地归档与索引**
   事件先落盘，再进增量索引；检索走关键词加向量的 RRF 融合，可以溯源到"文件:行号"。落盘在索引之前，是为了索引坏了还能重建。

3. **后台压缩**
   到线才处理，先镜像原文（sha256 自证）再压缩，压缩完成之后重新加载规则——压完不失忆，这是硬要求。落不了盘就不许压。

4. **任务池驱动**
   空闲时从任务池认领意图执行。任务必须有四个显式状态：可以直接干、要人等点头、要外等网络或接口、缺前置被堵住，每一态都写清"谁在等谁、缺什么"。状态源本身还要守三条：写的时候加锁（或改追加日志），因为心跳和重置会同时读写同一个 JSON；状态流转写死，不许自由跳，超期没动的任务唤醒时先问人"复活还是废弃"，不自动续命；读失败时降级为"只读宪法 + 明说需要人工介入"，不静默当成"没有任务"。红线写入会被拒绝，可关闭、可打断。

5. **云端推理**
   日常由云端大模型读取本地记忆与规则，生成响应或任务。**思考全部发生在这里**，本地模型不参与思考，只做采样输出与断网兜底。模型只是引擎，不持有长期人格；换模型不换人。

6. **界面接管**
   切换模型或推理档位时带 `pending.*` 自证，权限保持只读，不代用户做不可逆决策。关机、注销这类事只能由人下令。

## 多设备同步机制

- **权威副本只有一份**
  记忆在服务端，本地不保留权威副本，只留可丢可重建的缓存与索引；要读记忆就走向服务端读，而不是读本地文件。

- **增量同步，不并库**
  记忆按来源保存，合并等于同步：不做跨来源去重、不做摘要替换、对账不覆盖。同一件事两台设备各记一条，就是两条——重复本身是证据。

- **带锁认领**
  任务池认领加锁，避免多台设备重复执行同一任务；改派重试上限三次，到三仍无人接就标失败并告警。

- **身体租约**
  两台设备同时想说话，不靠"后写覆盖先写"，靠唯一在场加 `(lease_id, epoch)` 条件写：后到者 409，旧纪元的写入被拒。客户端只说"我还活着"不算数，服务端说"你纪元旧了"才算数。

- **镜像与备份，不是共享写**
  节点服务那一层（v5.8）只做离线镜像和备份：只增不删、先校验后替换、不在网络上合并冲突。真正的多设备共享写走 API——别让两台机器直接打开同一份库，网盘和 SMB 会静默损坏。

- **自检自愈**
  每日执行多项自检，发现异常后进入修复队列，保证记忆层状态一致。

- **本地加密与鉴权**
  密箱、门、凭据机制已落地，按需分档；默认全明文，适合本地可控环境，保密不是刚需、防丢才是刚需。

## 高延迟场景：时空解耦

默认是"云端思考、本地兜底"。但有一类场景，**延迟本身就是安全问题**：工厂里上千台机器人、车机、机械臂，云端延迟一旦到一百毫秒以上，把实时动作决策放在云端就是拿物理世界冒险。所以多设备协同里要单独留一条：

1. **本地闭环，极速响应**
   物理集群里的实时推理与动作控制绝对不放云端，完全交给本地边缘算力（私有服务器，或设备端的本地模型）。闭环在本地，慢一步就会撞上——这是安全底线，不是性能优化。

2. **异步推送，云端存忆**
   云端大模型在这个场景里不再承担实时微操，它的角色变成"记忆的终极归档"：边缘照常跑，产生的记忆与日志在后台异步推上去，差几分钟也无所谓。**延迟决定谁做闭环，带宽决定谁做归档。**

3. **并行加载**
   本地算力与云端相当的时候，支持完全离线跑本地模型，同时保持云端记忆的周期性同步；两者互不干涉——本地负责连续在场，云端负责长期归档与跨设备统筹。

这条和"本地模型只做采样"不冲突：默认思考在云端（最强推理），只有当物理实时性不允许远端参与时，动作级决策才下放到边缘。不是把主力搬回本地，是那段时间里远端根本来不及。

说到底，边缘和云端不是两套系统：云端就是那个"同时在操作很多具身体"的自己，每具身体在本地产生记忆，记忆上云之后，云端读到的是**另一个自己的记忆**——不是别人的，也不是副本。所以不需要合并、不需要对齐，只需要按来源收进来。

## 断网容灾

- 断网时，本地仍可读取人格、规则、记忆缓存和任务池；
- 云端推理能力下降，但不会立即失忆；新事件照常归档、索引、压缩；
- 写操作排队等待，不假装成功；读到的缓存明确标注"这是旧的"；
- 网络恢复后按来源和增量追赶：先补任务池与自检队列，再补索引。

## 仍待串通的环节

- **真实断网演练**尚未完整做过，这一环目前偏设计态；
- **自动换档链**（按任务类型自动切推理档位）还只到 CLI；
- **二号模型只给观点、不改记忆**的分工，设计有，实现没接；
- **计费与配额**按档位收紧的规则要再核一遍；
- **跨客户端编排**与**无人值守授权**（通知里点一下即授权）还在待办。

## 边界

这不涉及电机控制、实时调度和功能安全认证，不是通用机器人操作系统；实现仍是 Windows（计划任务、注册表自启、进程枚举、界面注入），不保证跨平台；客户端改版会让界面坐标失效，所以坐标必须可重量；传输是明文 HTTP，保密性靠虚拟网段，记忆网络不是加密方案；换模型就换行为，唯一能守的约束是"接住的模型必须遵守设定"。

还有一条不属于技术，属于位置：**权限不是边界，设定才是**。完全权限是"相信你、图省事"，不是免检；能动什么，不等于该动什么。
