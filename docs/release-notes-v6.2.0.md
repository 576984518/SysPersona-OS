## 一句话设问

**记忆存在本机文件里，那"谁能读、怎么读、丢了怎么办"这三件事，靠什么保证？**

## 设计思想

前面几版解决"记得住"，这一版解决"守得住"。守不是加密那么简单：加密了却每次都要人输口令，人就会把口令写在便签上；把门做得太重，最后被绕过。

所以分开做三件：**密箱**（东西怎么存）、**门**（谁来开）、**凭据**（开了之后能干什么）。三件都可以按档位调，默认是最松的那档——**保密不是这套东西的刚需，防丢才是**。把默认档设成"全明文"，是承认现实，不是偷懒。

## 做成了什么

**密箱**：AES-256-GCM 容器，口令走 Argon2id 派生；写盘一律「临时文件 → fsync → 替换」，中途崩了不会得到半个容器。容器格式公开写进 `docs/SECURITY_SPEC.md`，任何人都能拿它写一个读取器，不需要这份代码——数据主权不是一句口号，是格式公开。

**门**：是否加密、什么档位、什么条件下要求开启，写成可读的状态文件（`ops/vault.json`）。门的动作就四个：`seal` 封、`unseal` 解、`rekey` 换钥、`rebind` 换绑，每个动作要么整体成功，要么回滚，不留半开状态。

**凭据**：分档的权限凭据，短时有效。开过之后干什么都留审计，审计不写密钥本身。

## 证据

- 可行性报告 46 项全通过（Windows，Python 3.12 + OpenSSL 3.5），耗时约 35 秒，报告在 `docs/SECURITY-FEASIBILITY.md`；
- 加密容器与门在真库上跑过：封、解、换钥、回滚，各一次通过；
- 一条被量出来的事实：原型里每次密码学调用要起一个 Node 进程，约 **85 ms**，一次解封 4 次调用就是 340 ms——这 340 ms 是进程启动，不是密码学；真实现把 Provider 放进进程内就没有了。

## 边界

- **只解决"存"和"开"，不解决"同步"**：跨设备传输是本机→NAS→网盘→镜像盘这条外部链路的事，不在本项目里；
- 默认**全明文**。想要保密，要自己开档；开了档，口令丢了就是真丢了，没有后门；
- 不做"防物理接触"的承诺：拿到机器、拿到内存、拿到明文口令，任何本地加密都会失守；
- 不假装有密钥托管或找回机制——**没有找回，才是这套东西的诚实之处**。
