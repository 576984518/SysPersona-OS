# 后台处理（BACKGROUND SPEC）— v5.4

> 状态：**已交付 v5.4.0（2026-11-10）**——镜像 + **自动压缩闭环**都通了：水位到线 → 程序自己发
> `/compact` → 壳真的压下去（实测 379K → 18K），全程没人按。上一版运行时 v5.3.0（保活 + 交互代理）。
> 一句话：**到线才动，不提前清；清之前先落盘；压归壳，我们只管量和敲。**
>
> v1.6 补的是什么：**读数的来源换了一处**——不再自己算，直接读壳的 `contextPressure`（§2.1）。
> 这不是换算法，是承认"同一个数只能有一个来源"。
> v1.5 补的是什么：**"清之前先落盘"从要求变成硬闸**——链路里加了一步"现导 → 镜像 → 校验"，
> 落不了盘就不压（§六、§七）。**不动的东西**：四动作顺序、镜像规范、不改写历史、删除要人点头。

## 一、为什么要有这一版

上下文满不是"突然"的：它一路涨，直到某次请求被拒，才发现前面几十轮全是废料。
手动清理依赖人记得——他不该记得。所以：**监测归程序，决定归水位线，人只保留否决权。**

## 二、水位梯子（同一把尺子）

| 档 | 线 | 动作 | 谁批准 |
|---|---|---|---|
| 注意 | 150K | 只提示，不动作 | 自动 |
| 准备 | 250K | 可以把接续包备好 | 自动 |
| 该交接 | **300K** | **先镜像**（整段会话全文落盘）→ 再出接续包 | 自动 |
| 该压 | **350K** | 敲 `/compact`（借壳自己的压缩） | 自动，冷却 900 秒 |
| 断 | 1M / 请求被拒 | 出包 + 提示换窗口 | 自动，**不改写历史** |

**为什么从 300K/600K/800K 改成这条梯子**（2026-11-10，写下来防下次又倒挂）：

800K 那条线上，**自动压缩永远等不到**——壳自己的压缩线是 `0.35 × 1,048,576 ≈ 367K`，
人根本活不到 800K：要么中途手动压了，要么先被壳压掉。于是"到 800K 先镜像再压"变成一条
**只在纸上成立**的规则，判据①挂了一个多月没发生，就是这么来的。

所以梯子按**真实到得了的线**重排，并把镜像线（300K）压在壳的压缩线（367K）之前约 67K：

```
150K        250K        300K              350K        367K         1M
 |           |           |                 |           |            |
 注意        备包        镜像→出包         我们敲压     壳自动线      断
                          (原文先落盘)       (冷却900s)
```

顺序不变：**监测 → 镜像 → 压缩 → 归档**。镜像线早于压缩线，是这条链唯一不能调换的地方。

"满 100" 的口径沿用旧约定：每跨过 100K 整数倍提醒一次，不另立第二套计数。

### 2.1 尺子只有一把——就用壳记的那个数

**读哪里**：`~\.dsh\storages\session_projcache\sessions\session-<id>.json` 的 `contextPressure`。
壳每步都在更新它，里面两个数：

| 字段 | 是什么 | 谁在用 |
|---|---|---|
| `pressureTokens` | 最近一次调用的 `cacheRead + 未缓存输入`——**壳判"要不要压缩"就用它** | 我们判定、托盘、`persona_compact` |
| `surfaceTokens` | 界面上「消息占用」那个数（system + tools + messages） | 人眼在界面上看到的 |
| `contextWindow` | 模型窗口（1,048,576） | 百分比分母 |

**为什么不再自己算**（2026-11-10，这是"水位不匹配"的根因）：
以前用 `Δ(cacheRead+input)/Δcalls` 推——那是**一段时间内的平均值**。窗口里只要有一次压缩前的大调用，
平均值就被拉高：压缩刚发生时我们报 18K、壳报的是真值；过了一会儿我们又报 130K、壳报 139K。
**平均值冒充瞬时值，读数就永远跟壳对不上。** 壳已经记着，就不要再算第二份。

两个数的关系要讲清楚，否则会以为"两边打架"：`pressure ≥ surface` 是正常的——
`pressure` 含被缓存重读的历史前缀（模型实际要处理多少），`surface` 只算消息正文。
**判压缩用 `pressure`**（壳就是这么判的），**向人解释用 `surface`**（界面上看到的就是它）。

| 名字 | 是什么 | 参不参与判定 |
|---|---|---|
| **pressure**（现 147K） | 最近一次调用的真实 prompt 量 | ✅ 就用它 |
| **surface**（现 86K） | 消息正文占用，界面上显示的那个 | ❌ 只给人看 |
| **缓存累计**（如 97M） | 整个会话累计命中缓存的量，每次调用都累一遍 | ❌ 不是上下文 |
| 输出 / 调用次数 / ¥ | 计费与统计 | ❌ |

**兜底顺序**（没有 DSH 会话时才往下走）：壳口径 → 账本增量 → Hermes `turn_stats`（另一个客户端的库）→ 账本平均（标 `~`）。

**代码侧唯一出处**：`persona_limits.py`（`OK/WARN/CLEAN/MIRROR/LIMIT/PACK_LIMIT`）。
`persona_gauge.py`、`persona_daemon.py`、`persona_compact.py` 都认它，**不许各写一份数字**——
两处阈值不一致时，脚本说"该清理了"、CLI 却说"健康"，等于没有提醒（2026-11-08 踩过）。
`t_hctx` 落 `ops/hctx.json`：`{at, session, model, ctx, max, pct, level}`；压缩自己的账落
`ops/compact.jsonl` 与 `ops/compact-state.json`（最后一次开火的时间与水位）。

> **代价要写明**：这个读数只在 DSH 里成立——换一个不写 `session_projcache` 的客户端，就得重新接。
> 我们宁可"只对一种壳有效但数是真的"，也不要"到处都能算出个数但没有一个是真值"。

### 2.2 水位统计：四个数都对，但只有一个是水位

`python persona_gauge.py --stats` 直接把这张表打出来。为什么需要它：
界面上同时显示 **122M tok / 输入 455K / 22%** 三个数，人一眼看不出哪个是"上下文"；
我们这边又同时有 pressure / surface / 账本日均 / Hermes 四个数。**全是真的，但只有第一行是水位。**

| 数 | 实例 | 是什么 | 能不能当水位 |
|---|---|---|---|
| **pressure** | 239K（22.8%） | 最近一次调用的 `cacheRead + 未缓存输入` | ✅ **是水位**（壳按它判压缩） |
| surface | 141K（13.4%） | system + 消息正文（**不含 tools**） | ❌ 只是界面上的"消息占用" |
| 未缓存输入（累计） | 458K | 本会话所有调用里没命中缓存的输入**总和**＝界面上的「输入 455K」 | ❌ 累计量 |
| 缓存命中（累计） | 123.78M | 本会话累计命中＝界面上的「122M tok」 | ❌ 累计量 |
| 账本日均 | ~173K | `(cacheRead+input)/calls`，全历史平均 | ❌ 只兜底 |

**最容易误读的是「输入 455K」**：它是**这个会话里所有调用**的未缓存输入加总，不是"现在带了多少"。
把它当水位，会得出"已经 455K 该压了"的错判；把「122M」当水位，会得出"还有 122M 可用"的反向错判。
**百分比只有 pressure 算得出来**——界面那个 22% 就是 239K / 1.05M。

## 三、四个动作

| 动作 | 做什么 | 不做什么 |
|---|---|---|
| **监测** | 每 120 s / 每 5 分钟读一次真实 token 用量 | 不猜、不按字数估 |
| **镜像** | 到 300K，把当前会话全文写成一份 `.md` | 不做"摘要代替正文" |
| **压缩** | 到 350K，敲 `/compact`——**壳压自己的历史** | **不由我们改写历史**，不自研压缩算法 |
| **归档** | 镜像落 `archive\日期\`，进索引 | 不删任何原文 |

顺序写死：**监测 → 镜像 → 压缩 → 归档**。没镜像就压，等于拿记忆赌运气。

### 3.1 每一档的输入 / 输出 / 失败

```
监测：  gauge 读成本账本 + 会话文件  ──►  一个数（token）+ 一个档位
镜像：  sessions\<日期>\<来源>\*.md   ──►  archive\<日期>\<来源>\<会话id>-mirror.md
压缩：  /compact（8 个字符）          ──►  壳把旧历史换成摘要，水位回落
归档：  mirror.md                     ──►  index\L1.jsonl 多一行（persona_index_l1.py）
```

**压缩为什么只是"敲 8 个字符"**：压缩要读历史、判断哪段能丢、写成摘要——**只有壳自己干得对**，
因为它手里才有完整对话。我们在这条链上的职责只有两件：**量得准**、**敲得准**。
自研一套压缩，等于在没有原文的地方做摘要，压完必然对不上账。

## 四、镜像文件规范（v1.1 新增，落地时照抄）

**路径**：`archive\<YYYY-MM-DD>\<来源>\<会话id>-mirror.md`；`<会话id>` 取原文件名去扩展名，不另编新号。

**文件头**（必须逐行齐全，`blocks()` 靠它识别设备与底座）：

```
- 会话：<会话id>
- 设备：<主机名或"网页">
- 底座：<模型名，如 deepseek-web>
- 镜像于：<YYYY-MM-DD HH:MM:SS>
- 触发：hctx=<数字> / 线=<300000>
- sha256：<原文全文的 sha256>
- 原文：sessions\<日期>\<来源>\<原文件名>
```

**幂等**：同名 mirror 已存在且 `sha256` 相同 → 跳过并记一行日志；不同 → **不覆盖**，改名 `<会话id>-mirror-<HHMMSS>.md` 再写。
理由：镜像是证据，不是缓存；覆盖等于把上一份证据擦掉。

**不许做的事**：不许只写摘要、不许截断尾部、不许把 `## 用户/助手` 层级压平——压平后检索按块切不出来，等于镜像了读不到。

## 五、判据（三条，缺一不算成功）

1. **自然触发一次**：没人按、没人记得，程序自己量到线 → 自己把 `/compact` 敲进去 → 水位真的回落；
2. **镜像可读**：压缩前的全文在 `archive\` 里能逐字读出，且 `sha256` 与原文一致；
3. **断网回退一次**：云端不可用时，落本地/免费档，且**不丢这一轮**。

> 现状（2026-11-10）：**第 1 条已过**——379K ≥ 350K，冷却已过，程序自己发 `/compact`，
> 壳把旧历史换成摘要，水位 377K → **18K**，两个日志文件都有这一笔。
> **第 2 条已过**——`ensure_mirror()` 现导一份（231 KB）→ 镜像进 `archive\2026-11-10\电脑会话\`，
> `persona_mirror.py --check` 回 `OK … 一致`（sha256 与原文相符）。
> 第 3 条仍缺一次真实断网。

## 六、压缩：改走界面层（v1.4 重写）

**上一版为什么留空**：壳的压缩**接口**没有稳定契约——`compact` 在 DeepSeek 系模型上填不出嵌套参数
（实测结论，不是估计）。没有契约就调，等于把"压缩"写成"碰运气"。

**这一版换了问法**：不接口。壳里本来就有 `/compact` 这个命令，人能敲、壳认账——**那就不需要契约，
只需要一只手**。我们已经有注入通道（B71，本来是给唤醒简讯用的）：找窗口 → 点输入框 → 剪贴板 → `Ctrl+V` → 回车。
于是压缩从"接一个没有契约的接口"变成"复用一条已经跑通的通道"，一天之内从 `PENDING` 变成能跑。

### 6.1 闭环链路

```
  每 5 分钟（Windows 计划任务 SysPersona-Compact，pythonw，无窗）
        │
        ▼
  persona_compact.py check
        │
        ├─ ① 量：gauge 读出壳记的 `pressureTokens`「[上下文] 147K」
        │        （**壳判压缩用的就是同一个数**；不是累计缓存，也不是区间平均值）
        │
        ├─ ② 判线：377K ≥ 350K ?  ── 不到 → 记 idle，收工（不打扰任何人）
        │        │到线
        │        ▼
        ├─ ③ 判冷却：距上次开火 < 900 s ? ── 是 → 记 cooldown，收工（不连压）
        │        │冷却已过
        │        ▼
        ├─ ④ 先落盘：把当前会话导出成 .md → 镜像进 archive\ → 校验 sha256
        │        └─ 落不了盘 → 记 no-mirror，**这轮不压**（§七 唯一不可降级的一条）
        │        │落盘成功
        │        ▼
        ├─ ⑤ 不打断：GetLastInputInfo —— 他最近 5 秒还在敲，就等一会
        │        │
        ├─ ⑥ 敲：点输入框 → 剪贴板塞 `/compact`（8 字符）→ Ctrl+V → 回车 → 还原剪贴板
        │        │
        ├─ ⑦ 壳自己压：旧历史 → 摘要，旧上下文不再随请求上送
        │        │
        └─ ⑧ 留痕：ops/compact.jsonl（fired / idle / cooldown / no-mirror）+ ops/compact-state.json（last_fire, last_ctx）
                 │
                 ▼
        下一轮 gauge 读到的水位已经回落（377K → 18K）
```

一条闭环里**只有 ⑥ 是"动别人的界面"**，其余全是读文件、导文件、算数、写日志。这也是它能一天接上的原因：
那些步骤在前几个版本里都已经跑熟了。

**④ 为什么要现导一份，而不是复用半小时前那份**：差的这几十分钟，正是刚聊出来的内容——
把它压掉，等于把最该留的丢了。所以每次开火都现导（导出一次约 1–2 秒），只在一分钟内重试时复用。

### 6.2 四条纪律（缺一条就别叫自动）

| 纪律 | 为什么 | 落在哪 |
|---|---|---|
| **到线才动** | 提前清 = 凭空丢掉还有用的上下文，且没有任何收益 | `--threshold 350000` |
| **不连压** | 一次压缩后水位读数要过一会儿才回落；期间重复开火会连发多条 `/compact`，把对话搅乱 | `--cooldown 900` + `ops/compact-state.json` |
| **先落盘再压** | 镜像没落盘就压，等于拿记忆赌运气；这条是硬闸，不是提示 | `ensure_mirror()` 返回 False 就 `return 1`，日志记 `no-mirror` |
| **不打断人** | 他正在打字时把 `/compact` 敲进去并回车，等于替他发了半句话 | `GetLastInputInfo` / `--wait-idle` |

追加一条：**闹钟不挂在会话里**。第一版把这 5 分钟一次的检查登记在会话自己的调度器上，
结果压缩一发生、会话被换掉，闹钟跟着消失（事后 `schedule_list` 是空的）。
**能穿越会话的只有系统级计划任务**——所以现在是 Windows 计划任务，不是会话闹钟。

### 6.3 失败时怎么办

- 量不到水位（gauge 报错）→ 打印 `FAIL`、退出码 2，**不猜、不发命令**；
- 导出 → 镜像失败 → 记 `no-mirror`，**这轮不压**（退出码 1），下一轮再来；
- 注入失败（找不到窗口 / 焦点没拿到）→ 记 `fail` 到 `ops/compact.jsonl`，**不重试**——下一轮 5 分钟后自然再试；
- 壳不认 `/compact`（升级后改口径）→ 表现为"发了但水位不降"，`ops/compact.jsonl` 里会留下连续 `fired` 而水位不降的证据，
  这比静默失效好查。

## 七、失败与降级矩阵（v1.1 新增）

| 失败点 | 现象 | 降级动作 | 告警 |
|---|---|---|---|
| 读不到账本 / Hermes 库被锁 | `ctx` 为空 | 保持上一轮读数，标 `stale`，不触发镜像 | 连续 3 次 → `ops\alerts.jsonl`（warn） |
| 导出失败（node 不在 / 会话目录找不到） | 没有新 `.md` | **不压缩**，记 `no-mirror`，等下一轮 | warn |
| 镜像写盘失败（盘满 / 占用） | 无 mirror | **不压缩**，直接出包 + 提示换窗口 | error |
| 镜像成功、索引失败 | mirror 不在 L1 | 保留 mirror，下轮 `index` 作业补 | warn |
| 压缩接口不认参数 | 返回错误体 | **本版不再走接口**；改界面层后此项作废（见 §六） | — |
| 壳不认 `/compact`（版本升级改了命令） | 发了但水位不降 | 停手，连续 `fired` 且水位不降即报警 | warn |
| 注入时找不到窗口 / 焦点没拿到 | 没发出去 | 记 `fail`，不重试，等下一轮 | warn |
| 会话文件正在被写 | 尾部半行 | 按行尾停在最后一个完整 `## 助手` 块，不写半句 | 无 |

**唯一不可降级的一条**：镜像没落盘，就不许往下走压缩。宁可这轮不压，也不能压完才发现正文没了。
**这条现在是硬闸**（`ensure_mirror()` 返回 False → 直接退出，不进注入），不是文档上的一句劝告。

## 八、容量与预算（v1.1 新增）

| 项 | 量级 | 备注 |
|---|---|---|
| 单次镜像体积 | 0.5–6 MB | 与源会话同量级，不压缩 |
| 每会话镜像份数 | 1（幂等） | 同会话跨天再触发 → 追加带时间戳的新份 |
| 索引增量 | 每份 1 行 | `L1.jsonl` 单行 < 1 KB |
| 磁盘占用 | 约等于 `sessions\` 的 1 倍 | 预留 2 倍即可，不做自动清理（删记忆要人点头） |

## 九、边界

- **绝不自动删记忆**：删除永远要人点头（红线）；
- 不替用户决定"这段不重要"——压缩只压上下文，不动库；
- 只作用于当前会话的上下文，不动 `sessions\` / `archive\` 的原文；
- **绝不自研压缩算法**：压是壳的活，我们只量、只敲（§六）；
- 失败就停：注入失败不重试，等下一轮；连续开火而水位不降就报警，不硬压。
