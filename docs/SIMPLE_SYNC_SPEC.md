# 简易网络同步 — SIMPLE_SYNC_SPEC

> 状态：**v5.7.0 交付**。参考实现 `tools/ctxpack/persona_cloud_bus.py`。
>
> 一句话：**不管网盘是谁家的、不管走什么协议，这里只规定一件事——多个程序共用一个目录时，
> 怎么写、怎么读，才不把文件写坏。**

## 一、它是什么、不是什么

| 是 | 不是 |
|---|---|
| 一套**读写纪律**（多进程共享目录时怎么落盘、怎么聚合） | 不是同步软件，不做传输 |
| 一个**最小参考实现**（我们自己用的那份） | 不实现任何网络协议，不自己搭服务器 |
| 对**存储的零假设**（只要是个能读写的目录） | 不绑定任何网盘、云厂商、客户端 |

**它故意写得很小**：真正的传输、加密、断点续传、冲突合并，全部交给现成的网盘或服务器去做。
我们只守住"文件别被写坏"这一层。

## 二、唯一的依赖假设

上层拿到的就是**一个普通可读写目录**——本地盘、映射盘、网络挂载都行，只要满足三条：

1. **能当普通目录读写**：`open / rename / listdir` 这些基本操作可用；
2. **写完能被别的进程看见**：不是只在某个客户端的内存/缓存里，确实落到了那一层；
3. **上传期间的锁要能绕开**：如果同步方会在上传未完成时锁文件，就不要直接改原名——
   写临时名再改名即可（见 §四.2）。

盘符、挂载点、账号、凭据，**全部由部署决定**，通过环境变量 `PERSONA_CLOUD` 指进来。
规范里不写死任何路径。

## 三、为什么不能直接改同一个文件

多进程直接改同一个文件，必然坏在三种地方：

| 坏法 | 现象 |
|---|---|
| 半截文件 | A 写了一半，B 正好读到 → 读到残缺 JSON |
| 互相覆盖 | A、B 同时读-改-写，后写的把前一个的改动吃掉 |
| 传输中断 | 同步方传到一半断了，远端留下 0 字节 |

下面四条纪律，就是分别对着这三种坏法来的。

## 四、设计逻辑（四条纪律 + 为什么这么定）

### 1. 分片写：谁写谁的，不写同一个文件

每个进程写自己命名的分片（`节点__标题__时间戳`），**不去 append 别人正在写的文件**。
竞争从"锁"降级成"零竞争"——这是最省事的一步。

### 2. 先写临时名，再改名（原子替换）

```
写 foo.md.tmp  →  落盘 fsync  →  os.replace("foo.md.tmp", "foo.md")
```

改名为原子操作：**观察者要么看到旧文件，要么看到新文件，永远不会看到半截**。
这一步同时绕开"同步客户端锁住未传完文件"的问题——被锁的是临时名，正式名没被碰。

### 3. 总索引单写手 + 文件锁

分片好办，但"总索引"（谁写了哪些片）是个聚合视图，天生只能一个人改。做法：

- 拿锁（非阻塞 + 超时）→ 读全部行 → 删同名旧行 → 追加新行 → 整体重写（同样 tmp→rename）；
- **拿不到锁就等，等到超时宁可这次不写**——少写一条索引可以补，写坏总索引要人工修。

### 4. 只移不删

删除是不可逆动作，而"多进程共享目录"最容易出现的错误就是**两边同时删**。
所以删改一律移进 `Archive\`，宁可占空间，也不真删。这条同时也是"删记忆必须人点头"的技术兜底。

## 五、目录结构（建议，不是标准）

```
<网盘根>\
├── Hot_Bus\          热数据：小分片，频繁写
├── Cold_Backup\      冷数据：压缩包，低频写
├── Archive\          删改都移到这里，不真删
├── MASTER_INDEX.md   总索引（单写手）
└── .master.lock      锁文件
```

**为什么分热冷两区**：同步方通常按队列传，大压缩包会把小分片堵在后面，热数据反而迟到。

## 六、读写流程

```
写：分片 → 网盘可用？
                 ├─ 是 → tmp→rename 写上去 → 持锁更新总索引
                 └─ 否 → 追加本地队列（不丢、不阻塞）

读：只读 MASTER_INDEX.md → 按需去 Hot_Bus\ 取某一片
```

读端**不扫全目录**：在网络挂载上目录扫描很贵，而且随文件数线性变慢。

## 七、断网怎么办

- 判定"可用"= `PERSONA_CLOUD` 指向的目录存在且可写；
- 不可用 → 追加到本地 `ops\cloud-queue.jsonl`，**进程不挂、不丢、不重试风暴**；
- 恢复后 `--flush` 补交，**幂等**（同名分片覆盖 + 总索引重算）；
- 队列本身是追加写 JSONL，崩在中间也只坏最后一行（读的时候跳过解析失败的行）。

## 八、和别的工作流的关系

抓取、上下文压缩、补交队列是**三条互不阻塞的线**：网盘慢只让补交慢，不卡抓取和压缩。

## 九、参考实现（我们自己的最小版本）

```powershell
$PY = "$env:USERPROFILE\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe"
$R  = $env:MEM
& $PY $R\persona_cloud_bus.py --status      # 网盘可用？本地排队几条？
& $PY $R\persona_cloud_bus.py --flush       # 补交队列
& $PY $R\persona_cloud_bus.py --read        # 打印总索引
& $PY $R\persona_cloud_bus.py --shard "会话总结" --body-file x.md
```

本机实测（2026-11-10）：

| 项 | 结果 |
|---|---|
| 未配置网盘 → 写 | `QUEUED`，本地队列 +1，进程不挂 |
| 配好后 → 补交 | 队列全量提交、清空 |
| 3 进程并发写 | 全部成功，**0 个 `.conflict`、0 个残留 `.tmp`** |
| 总索引 | 持锁重写、无重复表头、时间倒序 |

## 十、边界与声明（重要）

- **不实现协议、不绑定厂商**：传输、加密、重试都交给现成的网盘/服务器；
- **这是我们的最小实现，仅供参考**：你们可以直接用现成的同步工具，也可以按 §四 的四条纪律自己写，
  甚至可以只学那四条、完全不写代码；
- 我们的宗旨一直没变：**只写最小实现和可能，从不强求别人怎么做**。

**还没做的（如实写）**：真实网盘环境未验证（本机未配置 `PERSONA_CLOUD`）、`Archive\` 的 GC 独立线程未实现。

## 六、节点服务：一台机器当服务端，其余连它

> （本节按交付要求编号「六」；上面的原有 §六–§十 保持原样，本节位于文末。）

`persona_cloud_bus.py` 解决的是"多个程序共用一个目录时怎么写不坏"，传输本身还是交给网盘。
本节补另一半：**没有网盘、只有一台能互相 ping 通的机器时，节点之间怎么把索引和档案搬过去。**
参考实现 `persona_lanbus.py`（服务端 + 客户端一体，纯标准库，无第三方依赖）。

### 6.1 拓扑

```text
        ZeroTier / Tailscale：只负责"能通"，不碰数据
  ┌──────────────────┐        虚拟网段 10.x / 100.x         ┌──────────────────┐
  │ 节点 B（客户端）  │ ─────── HTTP :8737 ───────────────▶ │ 节点 A（服务端）  │
  │ python ... sync  │  GET  /health    GET  /manifest     │ python ... serve │
  │ 本地记忆库 B     │  GET  /blob      POST /blob（可选）  │ 本地记忆库 A     │
  └──────────────────┘                                     └──────────────────┘
        ▲                                                           │
        └──── 只拉"本地没有或 sha256 不同"的文件；先校验、再原子替换 ───┘
```

单写多读：一台当服务端（只读白名单 + 可写 `index/`），其余设备当客户端。
客户端默认只拉不推；需要回写时用 `POST /blob`，但**服务端不替你合并冲突**。

### 6.2 端口与鉴权

| 项 | 约定 |
|---|---|
| 端口 | 默认 `8737` |
| 监听 | 默认 `127.0.0.1`（只本机）。对外必须显式 `--bind <虚拟网卡地址>` |
| 令牌 | `PERSONA_LAN_TOKEN` 环境变量优先；其次 `%LOCALAPPDATA%\SysPersona\lan-token.txt` |
| 比对 | `hmac.compare_digest` 定长比较；**取不到令牌服务端拒绝启动**（退出码 2） |

- `/health` 免令牌，只回 `{ok, node, version, root, files}`，不含任何文件路径；
- `/manifest`、`/blob` 全部要求 `Authorization: Bearer <token>`，缺失或错误一律 `401`；
- 所有响应带 `X-Node: <主机名>`，日志里能分辨是谁；
- 每个请求一行写进 `ops\lanbus.jsonl`（时间 / 方法 / 路径 / 字节数 / 结果 / 来源 IP），**不记令牌**；
- 启动时打印本机所有 IPv4，并提示"只在虚拟组网网段暴露"；`--bind 0.0.0.0` 额外告警。

`--bind 127.0.0.1` 是默认安全档，只适合本机自测；跨设备必须显式绑定虚拟网卡地址。
传输是**明文 HTTP**（没有 TLS），令牌在请求头里，保密性完全依赖虚拟网段的加密。

### 6.3 白名单

| 目录 | 服务端 | 客户端 |
|---|---|---|
| `index/` | 读 + 写（同步产物） | 可拉、可回写 |
| `archive/` | 只读 | 只拉 |
| `续接/` | 只读 | 只拉 |
| `ops/lanbus/` | 写（拉取暂存 / 拒收残片） | 本地暂存 |

- 请求里的 `path` 必须是**白名单目录下的相对路径**；
- 含 `..`、以 `/` 或 `\` 开头、带盘符或冒号（如 `C:\Windows\win.ini`）的请求直接 `400`；
- 服务端还会做 `realpath` 越界检查（防符号链接 / 目录联接跑出库根）；
- 白名单之外的一切路径（`memory/`、`sessions/`、`ops/*.json` 等）都不可达。

### 6.4 虚拟组网前提

ZeroTier / Tailscale **只负责连通，不管数据**：它们不校验文件、不做增量、不留版本。
本协议假设：

1. 两台机器在同一个虚拟网络里，能互相 `ping` 通、目标端口可达；
2. 服务端绑定虚拟网卡地址（或 `0.0.0.0` + 防火墙只放行虚拟网段），**不要**直接绑公网网卡；
3. 传输是明文 HTTP：令牌会出现在请求头里，所以**禁止**把 8737 映射到公网，
   也不要在不可信 Wi-Fi 上 `--bind 0.0.0.0`；
4. 两端系统时间不必同步（`mtime` 只用于展示，增量判定只看 `sha256`）。

### 6.5 防火墙放行（Windows，管理员 PowerShell）

只放行虚拟网段。示例用 ZeroTier 常见的 `10.147.0.0/16`，请换成你自己的网段：

```powershell
New-NetFirewallRule -DisplayName "SysPersona lanbus 8737" -Direction Inbound `
  -Protocol TCP -LocalPort 8737 -Action Allow -RemoteAddress 10.147.0.0/16
```

Tailscale 网段（`100.64.0.0/10`）再加一条，或只保留这一条：

```powershell
New-NetFirewallRule -DisplayName "SysPersona lanbus 8737 (tailscale)" -Direction Inbound `
  -Protocol TCP -LocalPort 8737 -Action Allow -RemoteAddress 100.64.0.0/10
```

确实要撤掉时再删规则：

```powershell
Remove-NetFirewallRule -DisplayName "SysPersona lanbus 8737"
```

> 默认 `--bind 127.0.0.1` 时不需要放行任何端口；规则只在跨设备访问时才需要。

### 6.6 失效边界

| 情况 | 表现 | 怎么办 |
|---|---|---|
| 设备离线 / 虚拟网卡没起来 | `sync` 连不上，退出码 4；本地文件不受影响 | 先 `ping` 对端，确认 ZeroTier/Tailscale 已连上；重跑 `sync`（幂等） |
| 令牌丢失 / 不一致 | `/manifest` 返回 401，`sync` 退出码 3 | 服务端 `python persona_lanbus.py token` 重新生成（重启 `serve` 生效），或核对环境变量；两端必须一致 |
| 版本不一致 | `/health` 的 `version` 与本端实现不同 | 以服务端版本为准升级客户端；`version` 变了就是协议不兼容，不要混跑 |
| 传输中断 / 写一半 | 客户端先写 `ops/lanbus/*.part`，sha 校验不过就不替换正式文件 | 重跑 `sync`；残片留在 `ops/lanbus/`，不会被当成正文 |
| 服务端磁盘满 / 没权限 | `POST /blob` 返回 4xx/5xx，客户端把它记进 `failed` | 修盘后重跑，`failed` 里的路径会重新出现在下次计划中 |
| 服务端文件正被改写 | `X-SHA256` 与实际字节不一致 | 本次判失败、不落盘；下次同步重试 |
| 客户端本地多出来的文件 | 不在清单里，因此不会被处理 | 故意如此：客户端**永不删除**本地文件，也不传播删除 |

### 6.7 它不解决什么

- **冲突合并**：两端同时改同一个文件，后同步的覆盖先同步的；没有三方合并、没有版本树；
- **多写并发**：服务端 `index/` 可写但没有跨节点锁；多台同时 `POST` 同一路径，最后落盘者赢；
- **离线队列**：客户端拉取失败只记在 `ops\lanbus.json` 的 `failed` 里，不会后台重试；
- **当网盘用**：没有断点续传、没有分块、没有去重、没有加密、没有配额；
- **删除同步**：只增不删。

一句话：它是"把索引和档案从 A 搬到 B"的最小通道，不是 Dropbox。
